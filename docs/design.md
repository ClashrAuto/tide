## 0. 三个目标在哪里打架

「低延迟 + 高吞吐 + 高安全」不是一个能同时拉满的三角。现有协议的差异，本质上都是在这三者之间选了不同的点：

- **延迟 ↔ 安全**：0-RTT 是延迟的终点，但 TLS 1.3 / QUIC 的 0-RTT 早期数据**没有重放保护**（TUIC 就吃这个亏）。要重放保护，通常就得退回 1-RTT。
- **吞吐 ↔ 抗识别**：填充与随机化是对抗流量分类的唯一手段，但每一个填充字节都是吞吐的直接损失（AnyTLS 的代价）。
- **吞吐 ↔ 公平/隐蔽**：Hysteria2 的 Brutal 靠无视丢包信号"抢"带宽，弱网吞吐确实碾压 TCP 系，但它同时制造两个问题——挤压同链路其他流量（易成为 QoS 的显眼目标），以及 QUIC over UDP 本身就是强特征。

TIDE 的思路不是"全都要"，而是**把这三组冲突从全局二选一，降级为局部动态选择**。下面每个机制都对应其中一组。

**同时要诚实地说明**：TIDE 的多数构件不是发明出来的，而是组合出来的——REALITY 的伪装、Vision 的零冗余加密、AnyTLS 的抗分类、MPQUIC 的路径调度都是既有成果。真正原创的只有三点：**单次票据**（让 0-RTT 与重放保护同时成立）、**前重后轻的填充预算**、**跨传输的会话解耦**。其余价值在于把这些正确的东西第一次放进同一个协议，而不是让用户在六个协议之间挑。

## 1. 架构

关键决策：**会话层与传输层解耦**。会话密钥、流状态、身份都不绑定到某一条 TCP 或 QUIC 连接，而是绑定到一个 Session ID 上。这是整个设计的地基——多路径、无缝迁移、0-RTT 全都从这里派生。

```
┌──────────────────────────────────────────────┐
│  入站：SOCKS / TUN / TPROXY / pf              │
├──────────────────────────────────────────────┤
│  TIDE 会话层（传输无关）                        │
│   · 流复用 + 亲和性调度（避免队头阻塞）           │
│   · 自适应填充（前重后轻）                       │
│   · 多路径调度器 + 路径质量探测                   │
│   · 会话密钥 / 单次票据 / 信道绑定                │
├────────────────────┬─────────────────────────┤
│  路径 A：TCP        │  路径 B：QUIC            │
├────────────────────┼─────────────────────────┤
│  外层：TLS1.3 /     │  外层：QUIC-TLS          │
│        REALITY      │        (+REALITY 变体)   │
└────────────────────┴─────────────────────────┘
        两条路径共享同一个会话，可并行、可切换
```

## 2. 机制 1：单次票据 0-RTT

**化解的冲突**：延迟 ↔ 安全。

现有方案的困境：SS-2022 用「时间戳 + 布隆过滤器」防重放，但它本就是零握手协议，没有票据概念；TLS 1.3 / TUIC 的 0-RTT 用会话票据，而票据**可重复使用**，所以早期数据天然可重放。

TIDE 把票据设计成**一次性**的：

1. 首次连接（1-RTT）成功后，服务端下发 N 张票据（默认 1024），每张 = `(ticket_id: u64, ticket_key: 32B)`，`ticket_id` 连续编号。
2. 后续连接时，客户端在**第一个应用数据记录**里出示一张票据并直接跟上载荷 → 0-RTT。
3. 服务端维护每用户的「未消费票据位图」。连续编号意味着 1024 张票据只需 **128 字节位图 + 一个基址计数器**。命中已消费的 → **静默丢弃并转发给掩护站点**（见机制 5）。
4. 每次连接增量补充票据，并设 24h 过期。

**一个漂亮的组合效应**：若外层使用 TLS 1.3 会话恢复的 early data（本身有重放问题），内层的一次性票据**恰好把外层的重放问题也一并堵死**——重放整个连接时，内层票据校验必然失败。两层的弱点互相抵消。

**代价（真实且不可忽略）**：服务端需为每用户维护 O(128B) 状态，且多节点部署时这份状态必须共享（Redis 或按用户一致性哈希路由）。这是本方案里唯一显著增加运维负担的地方，也是 0-RTT 的真实价格。如果部署形态是单机，成本可忽略；如果是多节点负载均衡，需要在二期实现前先定方案。

## 3. 机制 2：混合后量子密钥交换

密钥协商用 **X25519 + ML-KEM-768 混合**（ML-KEM-768 公钥 1184B、密文 1088B）：

```
k_shared = HKDF( X25519_shared || MLKEM_shared || transcript_hash )
```

理由是"先收割后解密"对代理流量是真实威胁——今天被记录的流量，十年后可被回溯解密，而代理流量的敏感性不随时间衰减。

**意外的协同效应**：Chrome 现已默认发送 `X25519MLKEM768` 密钥共享，ClientHello 因此膨胀到 1.2KB 以上。这意味着**带后量子的握手比不带的更像真实 Chrome**。在其他协议里安全与伪装是对立的（加密层数越多指纹越明显），在这里两者第一次同向。

这也是建议**现在就做、而不是留待以后**的原因：以后再加，就变成了"和当年的 Chrome 不一样"的新指纹。

## 4. 机制 3：显式协商的裸帧模式

**化解的冲突**：吞吐 ↔ 安全（表面上的）。

VLESS Vision 的洞察是对的：外层已经是 TLS 了，内层再套一层 AEAD 不增加任何实际安全性，只增加 CPU 与**包长指纹**。但 Vision 的实现方式是**探测内层流量像不像 TLS**再决定停止加密——这是启发式的，会误判。

TIDE 改成**显式协商 + 密码学前提**：

| 模式 | 内层 | 适用 |
|---|---|---|
| `sealed` | 内层 AEAD | 外层不可信（裸 TCP + 混淆） |
| `bare` | 明文长度前缀帧，安全性完全由外层承担 | 外层为 TLS 1.3 / QUIC **且信道绑定校验已通过** |

`bare` 的启用前提是机制 4 已经**密码学地证明**外层未被中间人替换。不是猜的，是证明的。

**⚠️ 这里原本写着"真正的吞吐收益在于它解锁了 kTLS：数据可在两个 kTLS socket 之间 `splice()`，用户态完全不接触负载"。查证之后这条是错的，两个独立原因各自致命：**

1. **`splice()` 与多路复用互斥。** 它成立的前提是这条 TLS 连接里流动的字节**恰好就是**某一条被代理连接的字节。而 TIDE 是多路复用协议：一条路径上交替着多条流的帧，每帧还带 type/flags/length/stream_id 头。用户态必须解帧才知道哪几个字节属于哪条流——既然必须解帧，数据就必然要进用户态。这一条与 kTLS 能不能用无关，是**协议形态**决定的。只有"一条连接一条流"的协议（Trojan、不开 mux 的 VLESS）才拿得到这个收益。
2. **Go 标准库不提供 TLS 流量密钥。** `crypto/tls` 只有未导出的 `setReadTrafficSecret`/`setWriteTrafficSecret`，没有任何导出 API，全库零 kTLS 支持。只能 `go:linkname` 进内部符号——跨版本随时会碎，而它保护的是加密密钥。

**bare 模式本身仍然是对的，只是收益要重新表述**：省掉内层 AEAD 的 CPU、消掉内层的包长指纹。这两项都实打实。至于"零拷贝转发"，它需要一个非复用的协议形态，与 TIDE 的会话层设计根本冲突——不是排期问题，是取舍问题。

## 5. 机制 4：信道绑定

内层认证消息必须包含外层的 TLS Exporter（RFC 5705）：

```
cb_hash     = TLS-Exporter("tide-channel-binding", 32B)
sealed_auth = AEAD(k_hs, user_id || timestamp || cb_hash || flags)
```

任何终止并重建外层 TLS 的中间实体（企业 MITM CA、CDN 回源、透明代理）都会导致 `cb_hash` 不匹配，连接**失败关闭**而非降级继续。

这一条同时是机制 3 的安全前提：只有确认外层是端到端的，才敢把安全性全部委托给它。

## 6. 机制 5：主动探测防御——关键在时序

伪装层沿用 REALITY 思路（借用真实站点的 TLS 指纹，无需自有证书）。但必须强调一个**大多数实现做错的细节**：

认证失败时不能"模拟"掩护站点的响应，必须**真的把这条连接的字节流转发给掩护站点**，包括其全部时延特征。

原因是——如果认证失败路径耗时 0.1ms，而真实站点路径耗时 50ms，探测方只需测量响应时间分布就能区分两者，伪装的全部内容随即作废。**时序是这里唯一真正难伪造的东西。**

所以规范要求：认证失败 → 该连接所有后续字节原样代理至掩护源站 → 直到连接关闭，全程不做特殊处理。代价是掩护站点必须真实可达且延迟合理（同机房或本机）。

## 7. 机制 6a：前重后轻的填充预算

对抗流量分类（TLS-in-TLS 的包长分布可被机器学习识别，正是 AnyTLS 要解决的问题）的关键观察：**分类器的判决发生在连接的前几百个包**，之后再怎么填充，对分类结果的影响急剧衰减。

因此填充分三阶段：

| 阶段 | 范围 | 策略 | 开销 |
|---|---|---|---|
| 1 · 判决窗口 | 前 64KB 或前 100 个包 | 每帧长度从拟合真实 HTTPS 浏览的混合分布中采样 | ~30% |
| 2 · 衰减 | 其后 256KB | 填充概率线性衰减至 0 | ~10% → 0 |
| 3 · 批量 | 之后 | 关闭填充，MTU 满帧 | 0 |

算笔账：一次 10MB 下载，总填充开销约 20KB，即 **0.2%**。而交互式流量本来就一直处于阶段 1——那正是它需要保护的地方。这比全程填充的均摊成本低一个数量级，抗分类效果却基本相同。

## 8. 机制 6b：多路径——不让用户选 TCP 还是 QUIC

线路质量决定该用 TCP 系还是 QUIC 系。既然如此，就不该让用户在配置文件里静态地选——应该让协议自己测。

因为会话层与传输解耦，同一会话可同时挂载 TCP 与 QUIC 路径：

- **默认从 TCP 路径起步**：1-RTT、享受内核 offload、长得最像正常 HTTPS。
- 后台建立 QUIC 路径（`PATH_PROBE` 帧，几乎零成本）。
- 按**路径评分**周期性把流迁到更好的那条。
- QUIC 路径被 UDP 封锁 → 拨号失败 → 全部走 TCP，**无需任何配置，无感降级**。
- 迁移无需重新握手，因为会话密钥不属于任何一条路径。

### ⚠️ 本节最初写错了一条，实测把它证伪了

原文写的是"当 TCP 路径丢包率持续超过阈值（默认 2%）时，逐步将批量流迁移到 QUIC 路径；
交互流留在 TCP（QUIC 的优势在丢包下的批量吞吐，不在小包延迟）"。**两句都不成立。**

**第一句按字面实现永远不会触发。** `PATH_PROBE` 走在 TCP 连接里，丢掉的段由内核重传，
探测最终总会到达，只是变慢——所以应用层测到的 TCP 丢包率恒等于 0。
实测（树莓派 5 ↔ x86，`netem` 5% 丢包）：同一时刻 TCP 路径报 `loss=0.00% / srtt=44.69ms`，
并存的 QUIC 路径 `srtt=1.26ms`。丢包在 TCP 上不表现为丢包，表现为 **RTT 膨胀**。
按丢包率写的判据一次都没触发，QUIC 路径建起来了却只拿到 0.1 MiB，TCP 扛了 52.2 MiB。

**第二句低估了 QUIC 对交互流量的价值。** 前提"QUIC 的优势只在批量吞吐"隐含假设
TCP 的延迟劣势只来自重传本身。实际上更大的一块是**队头阻塞**：一条 TCP 连接上
复用的所有流，会被任意一个丢失的段一起挡住。所以丢包下 QUIC 对小包延迟同样有巨大优势，
交互流没有理由留在一条正在丢包的 TCP 路径上。

改成"按评分（`SRTT + 2×RTTVAR + loss×2000`）迁移、目标好 2 倍以上且连续 2 次观测成立"
之后，同一场景 p90 从 187ms 降到 **9ms**，p99 从 537ms 降到 **194ms**。
完整数据见 [`spec.md`](spec.md) §11.3。

教训比结论更值得记：**判据必须建立在能观测到的量上**。一个结构上不可能变化的指标
（TCP 之上的丢包率）当判据，失效时不会报错，只会安静地什么都不做。

**拥塞控制明确用 BBRv3，不用 Brutal。** 理由：Brutal 的收益部分是幻觉——它通过制造缓冲区膨胀与重传来"看起来"占住带宽，同时挤压同链路其他流量，使自己成为 QoS 的显眼目标。可提供有上界的 aggressive profile，但不能作为默认。

## 9. 与现有协议的定位

| | 建连延迟 | 重放保护 | 批量吞吐 | 弱网 | 抗主动探测 | 抗流量分类 | 后量子 |
|---|---|---|---|---|---|---|---|
| SS-2022 | 0-RTT | 有 | 高 | 差 | 中 | 弱 | 无 |
| VLESS+Vision+REALITY | 1-RTT | N/A | **最高** | 差 | **最强** | 中 | 无 |
| Trojan | 1-RTT | N/A | 高 | 差 | 强 | 弱 | 无 |
| Hysteria2 | 1-RTT | 有 | 中 | **最强** | 弱 | 弱 | 无 |
| TUIC | **0-RTT** | **无** | 中 | 强 | 弱 | 弱 | 无 |
| AnyTLS | 1-RTT | N/A | 中 | 差 | 强 | **强** | 无 |
| **TIDE** | **0-RTT** | **有** | 高 | **最强**(多路径+每流独立 QUIC 流) | **最强** | **强** | **有** |

再次强调第 0 节的话：这张表的"全面领先"大部分来自组合而非发明，且**不包含实现成熟度这一维**——见下节。

## 10. 威胁模型：诚实地说明不解决什么

**能解决：**

1. 被动 DPI 特征匹配 —— 外层 TLS 伪装
2. 主动探测 —— 失败关闭 + 真实转发（时序：掩护连接提前拨号 + 请求提前推出，**残留见下**）
3. 统计/ML 流量分类 —— 前置填充预算（**长度**维）+ 探测抖动与判决窗口内的心跳填充（**时序**维，部分）
4. 中间人（含企业 CA）—— 信道绑定，失败关闭（**这一条核过了**，见下）
5. 先收割后解密 —— 混合后量子（**静态封装 + 临时封装两处都是混合的**，见下）
6. 重放攻击 —— 单次票据（0-RTT）+ 信道绑定（1-RTT，见下）
7. 服务端事后被攻破 —— 前向保密限制损失范围（**会话数据**；握手消息与 0-RTT 早期数据除外，见下）

> 关于第 6 条：**单次票据只管 0-RTT**。1-RTT 的 `HELLO` 没有票据、也没有 nonce 缓存，
> 在 ±120 秒的时间戳窗口内是**字节级可重放**的。第 6 条那句话没有覆盖这一半。
>
> 最要紧的是被重放的 `HELLO` 可能带着 `session_id`（请求**加入**受害者的会话）：
> 若它成功，攻击者就能把一条自己控制的路径挂进受害者的会话，
> 调度器随时可能把受害者的流量派到那条路上去黑洞掉。内容它读不了
> （会话密钥推不出来），但足以让会话卡死。
>
> **归因已查清**（此前一版写着"待查"，原因是那条用例根本没在测它声称要测的东西：
> 受害者客户端手里有票据，它的 join 走的是 0-RTT，于是录到的是 `ZERO_RTT` 而不是
> `HELLO`——难怪把 `cb_hash` 比对摘掉毫无影响，cb 从头到尾就没参与）。
> 把钱包清空逼出真正的 1-RTT 之后，结论是干净的：
>
> | 重放的帧 | 挡住它的 | 负对照（把该机制拆掉） |
> |---|---|---|
> | 1-RTT `HELLO` | **信道绑定**（§5） | 重放**成功**，攻击者的路径挂进了受害者会话 |
> | 0-RTT `ZERO_RTT` | **单次票据**（§3.3） | 落到信道绑定上，返回 `ErrChannelBinding` |
>
> 两条都值得注意。第一行说明**信道绑定承的重比 §5 写的多**：它不只挡"终止并重建
> 外层 TLS 的中间人"，也是 1-RTT 握手唯一的抗重放手段——谁要动它得先看懂这一段。
> 第二行是意外收获：单次票据整个失效时，信道绑定仍然兜住了 0-RTT 重放，
> 两道防线在这里是叠着的。
>
> `TestReplayedHandshakeCannotJoinVictimSession` 两个子用例分别断言**具体是哪个
> 错误**挡住的，而不只是"被挡住了"——只断言结果的话，真正承重的那道防线被拆掉后，
> 用例还会因为另一个无关的原因继续绿。上一版就是这么把归因记错的。

> ⚠️ 关于第 5 条与第 7 条：它们各自成立，但曾经**不组合**——这是补前向保密时留下的口子。
> `ee` 一开始只做了 X25519：
>
> | 敌手能力 | 结果 |
> |---|---|
> | 只有量子计算机 | 挡住（`ikm` 里的 ML-KEM 那一半还在，`k_hs` 安全） |
> | 只有静态私钥（服务器被查抄） | 挡住（`ee` 还在，会话密钥安全） |
> | **两者都有** | **全部失守**：静态私钥重算出 `k_hs`，量子解掉 X25519 的 `ee`，会话密钥全还原 |
>
> 而这恰恰是**同一个敌手**——能查抄服务器的国家级对手，正是有能力"先收割后解密"的那一个。
> 把两条威胁分开列，很容易看不见它们的交集。
>
> 现在 `ee = X25519(临时,临时) || ML-KEM(客户端临时封装密钥)`。后者要求客户端在第一个
> 飞行里就发出自己的临时 ML-KEM **封装密钥**（1184 字节），服务端对它封装一次、
> 把密文放进 `ACCEPT`（1088 字节）——这正是 TLS 1.3 的 X25519MLKEM768 的做法，
> 浏览器早已在默认付这笔字节。
>
> 注意"到**静态**密钥的封装"不能省：它给的是**隐式服务端认证**（只有真服务端能解开
> `HELLO.sealed`），是 1-RTT 能成立的前提，与前向保密是两件事。两处封装各司其职。
>
> 代价：`kem_share` +1184、`ACCEPT` +1088、`zero_seal` +1184，多一次 ML-KEM 封装/解封装。
> **不增加往返，1-RTT 与 0-RTT 的性质都不变。**

> 关于第 4 条：机制本身是对的，但在 2026-08 之前**一条测试都没有**——
> 而它恰恰是整份威胁模型里最承重的一条。客户端在被强装根证书的环境里
> **会**信任中间人的证书（参考实现的测试配置用 `InsecureSkipVerify` 忠实模拟了这点），
> TLS 那一层不会报任何错，于是信道绑定是用户与全量 MITM 之间**唯一**的东西。
>
> 现在有两条：`TestMITMTerminatingTLSIsRejected` 真的起一个终止并重建 TLS 的中间人，
> 并断言它**确实中继了字节**（否则"被拒绝"可能只是没连上）；
> `TestChannelBindingIsPerConnection` 守的是更阴的那种失效——
> 导出器退化成常量或全零时，比对永远通过、握手全部正常、
> **所有功能测试照样绿**，而中间人畅通无阻。两条都对着"摘掉 cb 检查"和
> "让导出器返回常量"验过会失败。

> ⚠️ 第 7 条曾经是**假的**，2026-08 才补上。原先的握手里从头到尾没有任何服务端临时密钥：
> `ikm = X25519(客户端临时, 服务端**静态**) || MLKEM.Decapsulate(服务端**静态**, ct)`，
> 两项都只依赖长期私钥和线上可见的字节。于是"一份录音 + 事后拿到的静态私钥"
> 就能重算 `k_hs` → 解开 ACCEPT → 拿到 `session_id` 与 `ticket_seed` → 还原整条会话，
> 连同用那批票据做的所有 0-RTT 会话。对一个默认威胁模型里就包含"服务器可能被查抄"
> 的协议来说，这是最不该缺的那一条。
>
> 现在服务端每次握手另生成一对 X25519 临时密钥，公钥随 ACCEPT 发出、私钥用完即丢，
> 双方做一次 ephemeral-ephemeral（Noise IK 里的 `ee`）并混进会话主密钥。
> 攻击者事后拿到静态私钥仍然能重算 `k_hs`，但缺那把从未上线的临时私钥，
> 会话密钥就推不出来。代价是 ACCEPT 多 32 字节、每次握手多一次 X25519，
> **不增加往返，1-RTT 性质不变**。
>
> 仍然不前向保密的是：`HELLO.sealed`、`ACCEPT` 本身、以及 0-RTT 的 `early_data`——
> 它们必须在拿到对方临时公钥之前就能读，1-RTT 里躲不掉。
> 这与 TLS 1.3 的取舍完全一致（RFC 8446 §2.3 明确写了 0-RTT 数据不具前向保密），
> 也与 Noise IK 一致（`ee` 之前的消息只有弱前向保密）。绝大部分字节是会话数据，
> 那部分现在保护住了。

**不能解决（不要指望）：**

- **交互式流量的时序指纹**。突发模式与包间隔是网站指纹攻击的核心特征，唯一的**根治**手段是恒定速率掩护流量——那会直接摧毁本方案的低延迟目标。这是真实且无解的取舍，**不是待办事项**。

  > ⚠️ 但"根治不了"曾经被当成"一点都不做"，而那是两回事。2026-08 之前时序这一维是
  > **完全裸奔**的：路径探测用 `t.Reset(interval)` 的常量间隔，实测一条应用层完全静默的
  > 连接，线上包的到达间隔是 **均值 1000.2ms、标准差 0.15ms、变异系数 0.00015**——
  > 一个精确到 0.15 毫秒的节拍器。识别它连机器学习都用不上，对到达间隔做个直方图
  > 就一眼看穿。填充把**长度**修得再像 HTTPS 也救不回来：长度和时序是两个彼此独立的维度。
  >
  > 同一时期 `padding.go` 里的 `maybeHeartbeat`——注释写明它是用来填静默间隔的——
  > **从来没有被任何地方调用过**。等于机制 6a 只上线了一半。
  >
  > 现在：探测间隔加 ±40% 均匀抖动，且判决窗口内往静默间隔里以 0.35 的概率插
  > `PADDING` 帧（长度从同一张 HTTPS 分布表采样）。同样的测量，变异系数
  > **0.00015 → 0.69**，提升约 4600 倍。这属于学术上的 adaptive padding
  > （WTF-PAD 及 Tor circuit padding 框架都基于它）：往包间隔里注入假流量，
  > 而不是恒定速率发送。**它不能根治网站指纹攻击**，上面那句话仍然成立；
  > 它消除的是"这条连接有个 1Hz 节拍器"这种**不该存在的免费特征**。
- **失败关闭路径上残留的时序侧信道**。§7.1 要求"尽早判定"，于是不同探测在不同深度出局：
  一个 HTTP 请求第 2 个字节就被否掉，而一个长得像 `HELLO` 的探测要等服务端做完
  X25519 + ML-KEM-768 解封装才在 AEAD 上失败。那段运算时间会写进"多久之后掩护源站开始回话"。

  > 这是个**自足**的判据：探测方不需要任何对照基线，拿同一台机器自己跟自己比就够了，
  > 而真正的 nginx 对这两个输入没有任何时间差——两者都只是畸形请求。
  > 实测（本机掩护源站，长度对齐的两种探测各 400 次）：
  > **修复前 182µs vs 315µs，差 +73%，Welch t = 38.7。**
  >
  > 已做的：掩护连接的拨号提到读第一个字节**之前**——拨号完成的时刻与探测方发了什么
  > 完全无关，密码学运算被并行掉。差值降到 **约 +33%**。
  >
  > 提前**推请求**也试过（想让掩护源站的处理也并行起来），**一无所得**：
  > 加上它差值纹丝不动（64.1µs → 64.1µs）。掩护源站的响应在确认握手失败之前本来就
  > 不能回给客户端，请求早送并不能让响应早到。而代价是实在的——那样每一条**合法**
  > 握手都会把加密后的握手帧漏给掩护源站，掩护源站于是为每次正常连接记一条畸形请求
  > 日志（谁看得到那份日志就能数出 TIDE 的握手次数；掩护源站若是第三方站点，
  > 还等于替用户往别人服务器上发垃圾）。已删除，spec §7.3 写成 MUST NOT。
  > 既有实践（Xray/Trojan 的 fallback）也是同一条线：只有认证失败才碰后端。
  >
  > 剩下这 33% 短期内消不掉，因为**掩护源站的字节在确认握手失败之前绝不能回给客户端**——
  > 任何走到密码学那一步的探测都必然要等它。彻底抹平只有两条路，都更糟：对所有输入
  > 都做一遍 KEM（4 字节的探测就能换一次 ML-KEM 解封装，正是 RFC 9000 §21.9 那类放大），
  > 或者给失败响应加固定下限（所有畸形请求恰好耗时 T，本身又是特征）。
  >
  > 实际可利用性取决于噪声：真实网络上探测方的 RTT 抖动通常 ≥1ms，要从中分辨 64µs 的
  > 均值差需要每类上千次探测，而每次都是一次完整 TLS 握手。**不是不可利用，是变贵了。**
  > `TestFailClosedTimingDoesNotLeakHandshakeDepth` 守住这条线不再退回去。

- **IP 封锁**。没有任何协议能解决，属于运营层面。
- **全局被动敌手的收发端关联**。需要混币网络级别的设计，不在范围内。
- **实现成熟度**。这是最大的实际风险：Trojan 有十年公开审计，TIDE 第一天只有一个实现。**一个设计上更好的新协议，在头两年里的实际安全性大概率低于一个设计一般但被审烂了的老协议。** 这一条应该压过第 9 节表格里的所有优势来考虑，也意味着不要在 UI 或文档里把 TIDE 宣传成"比 Trojan 更安全"。

## 11. 分期落地（已完成，附回顾）

原计划分三期、按收益/风险比排序。三期都已落地，回头看有两处判断需要修正：

### 一期（低风险，收益立竿见影）—— 已实现
机制 3（裸帧模式）+ 机制 6a（前重后轻填充）。

裸帧模式做完了。但它当初承诺的最大收益 kTLS + `splice()` **不成立**——
多路复用协议拿不到零拷贝转发，理由见第 4 节的更正。实际拿到的是省掉内层 AEAD 的
CPU 与内层包长指纹，这两项都实打实，只是没有原先吹得那么大。

### 二期（核心价值）—— 已实现并实测
机制 1（单次票据 0-RTT）+ 机制 4（信道绑定）+ 机制 2（混合后量子）。

票据多节点同步的方案在开工前定了（spec §12.1）：要求 `ConsumeAny` 原子 +
票据编号全局单调。后者不是随手加的约束——0-RTT 有个鸡生蛋，
查位图要先知道用户，而用户身份在待解密的密文里；全局单调编号让 `ticket_id`
本身唯一确定所属批次，才解开了这个环。

### 三期（最复杂）—— 已实现，但当初的风险评估反了

原文写"实现复杂度约等于前两期之和，而收益只在弱网线路上体现，建议先用二期的实测数据
判断值不值得"。实际情况是：

- **复杂度被高估了**：多路径本身很薄。真正的工作量在**为多路径做准备**的那部分——
  绝对偏移、累积确认、重传缓冲、RTO（spec §4）。而那部分**不是三期的成本，
  是二期就该有的**：没有它们，一次普通的 Wi-Fi 切换就会让流中间静默少掉一段字节。
  换句话说，"路径可以死"这个前提一旦成立，可靠性层就必须存在，与有没有第二条路径无关。
- **收益被低估了**：它不只在"弱网线路"上体现。任何会波动的链路——移动网络、
  家用 Wi-Fi、跨境线路——都在这个范围内，而那恰好是代理的主要使用场景。
  实测 p90 从 197ms 到 9ms 不是一个边缘优化。

如果重来一次，正确的分期是：把可靠性层（绝对偏移 + ACK + RTO）从三期挪到二期，
因为它是"会话比路径活得长"的必要条件；剩下的多路径调度反而是最薄的一层。
