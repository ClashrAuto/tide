## 1. 术语与约定

| 术语 | 含义 |
|---|---|
| 外层信道 | 承载 TIDE 的加密通道：TLS 1.3（TCP 路径）或 QUIC-TLS（QUIC 路径） |
| 会话 (Session) | 由 Session ID 标识的逻辑连接，**独立于任何一条路径存在** |
| 路径 (Path) | 承载会话的一条具体传输连接 |
| 流 (Stream) | 会话内的一条应用层字节流，对应一个被代理的 TCP 连接 |

- 所有整数为**大端序**。
- `varint` 采用 QUIC 变长整数编码（RFC 9000 §16）：首字节高 2 位给出总长度 1/2/4/8 字节。
- 版本字节 `0x02`（draft-02）。**线格式一变就必须改它**——它是"两端版本不一样"
  唯一能被明确认出来的途径，而且接收方 MUST 在任何长度相关的解析**之前**就检查它：
  否则旧版本的对端总是先在长度校验上出局，版本字节一眼都不会被看到。
- **握手消息**的 AEAD 恒为 ChaCha20-Poly1305（理由见 §3.0）。
- **记录层**的 AEAD 由 `ACCEPT.mode` 敲定：ChaCha20-Poly1305 或 AES-256-GCM。

## 2. 帧格式

所有 TIDE 通信（握手之后）由帧构成，帧位于外层信道内部。

```
 type(u8) | flags(u8) | length(varint) | stream_id(varint) | payload… | padding…
```

`length` 覆盖 `payload + padding` 的总长。

### 2.1 填充的定位

`PAD` 标志置位时，body 的**最后 2 字节**是大端 `u16 pad_len`，其前 `pad_len` 字节为填充：

```
body = payload || pad_bytes[pad_len] || u16(pad_len)
```

> draft-00 把 `pad_len` 写在填充区开头。那样接收方无法定位 payload 的结束位置——
> 它得先知道填充有多长才能找到 `pad_len`，而 `pad_len` 正是要找的东西。
> 放在末尾则只看最后 2 字节就能切开，没有任何歧义。代价是每个带填充的帧多 1 字节
> （相对 varint 的常见情形），而批量阶段根本不填充，不进吞吐关键路径。

填充内容 MUST 为零字节。它位于外层 AEAD 之内，密文与随机数不可区分，
生成随机填充是纯粹的 CPU 浪费。

### 2.2 帧类型

| type | 名称 | 方向 | 说明 |
|---:|---|---|---|
| 0x01 | `HELLO` | C→S | 首次握手，见 §3.1 |
| 0x02 | `ACCEPT` | S→C | 握手响应 + 首批票据，见 §3.2 |
| 0x03 | `ZERO_RTT` | C→S | 0-RTT 握手，见 §3.3 |
| 0x10 | `STREAM_OPEN` | 双向 | 新建流，见 §4.1 |
| 0x11 | `STREAM_DATA` | 双向 | 流数据，**带绝对偏移**，见 §4.2 |
| 0x12 | `STREAM_FIN` | 双向 | 单向关闭，payload 为 varint 最终偏移 |
| 0x13 | `STREAM_RST` | 双向 | 异常关闭，payload 为 u32 错误码 |
| 0x14 | `STREAM_ACK` | 双向 | 累积确认 + 流控通告，见 §4.3 |
| 0x20 | `DATAGRAM` | 双向 | UDP 数据报，见 §5 |
| 0x30 | `PATH_PROBE` | 双向 | 路径质量探测，payload = `u64 seq \|\| u64 sender_nanos` |
| 0x31 | `PATH_ACK` | 双向 | 原样回显 `PATH_PROBE` 的 16 字节 |
| 0x32 | `PATH_MIGRATE` | 双向 | 声明该流已迁至本路径，payload = varint 当前确认偏移 |
| 0x40 | `TICKET_REPLENISH` | S→C | 增量补充单次票据 |
| 0x41 | `TICKET_REQUEST` | C→S | 票据见底，请求补充 |
| 0x50 | `PADDING` | 双向 | 纯填充帧，接收方 MUST 丢弃 |
| 0x5F | `CLOSE` | 双向 | 关闭会话 |

未知 type 的帧接收方 MUST 忽略并跳过（依 `length`），以便后续版本扩展。

`PATH_ACK` **原样回显**探测帧的时间戳，因此两端不需要时钟同步——
发起方只用自己的两次读数做差。

### 2.3 标志位

| bit | 名称 | 含义 |
|---:|---|---|
| 0 | `PAD` | body 尾部有填充，见 §2.1 |
| 1 | `END` | 本帧为该流的最后一帧（等价于紧跟 `STREAM_FIN`） |
| 2 | `PUSH` | 提示立即冲刷，不要等待聚合 |
| 3–7 | — | 保留，发送方 MUST 置 0，接收方 MUST 忽略 |

### 2.4 上限

- 单帧 body MUST ≤ 56 KiB。接收方 MUST 在 `length` 超限时立即失败关闭——
  没有这个上限，对端只要声明一个巨大的 `length` 就能让接收方预分配等量内存。
- `sealed` 记录的明文 MUST ≤ 60 KiB（§6.1）。帧 MAY 跨记录边界。

## 3. 握手

### 3.0 握手消息的 AEAD

握手消息（`HELLO.sealed_auth`、`ZERO_RTT.sealed`、`ACCEPT`）的封装 MUST 使用
**ChaCha20-Poly1305**，与两端有无硬件 AES 无关。

> 接收方在解开这条消息之前无从知道对方用了什么算法——`flags` 就在密文里。
> 依次尝试两种算法会让"认证成功"与"认证失败"产生可测量的时间差，
> 而这正是 §7 反复要求消除的东西。记录层（批量数据）才是 AES 值得快那 2–3 倍的地方，
> 由服务端在 `ACCEPT.mode` 里一锤定音。

### 3.1 `HELLO`（首次连接，1-RTT）

在外层 TLS 握手完成后，作为**第一个应用数据记录**发送。

```
HELLO {
    version       : u8 = 0x01
    kem_share     : X25519_pub(32) || MLKEM768_ct(1088) || MLKEM768_ek(1184)   // 2304 字节
                    // 前两段：到服务端**静态**密钥的封装（隐式服务端认证）
                    // 第三段：客户端**临时** ML-KEM 封装密钥，供 §3.2 的 ee 用
    client_random : 32 bytes
    sealed_len    : u16
    sealed_auth   : AEAD(k_hs, auth_plain, ad = transcript)  // nonce = 全零
    early_data    : opt bytes
}

auth_plain {                       // 77 字节
    user_id    : 16 bytes
    timestamp  : u64               // Unix 秒
    cb_hash    : 32 bytes          // 见 §5
    flags      : u8                // bit0 请求 bare；bit1 本机有 AES-NI；bit2 加入已有会话
    session_id : 16 bytes          // 全零 = 新建会话；否则请求加入该会话（§9）
    path_id    : u32               // 本路径在会话内的编号
}

transcript = SHA256( version || kem_share || client_random )
k_hs       = HKDF( ikm  = X25519_shared || MLKEM_shared,
                   salt = client_random,
                   info = "tide/draft-01 handshake" || transcript )
```

`X25519_shared` 由客户端临时私钥与**服务端静态 X25519 公钥**协商；
`MLKEM_shared` 由客户端向**服务端静态 ML-KEM-768 封装公钥**封装得到。
两者一并作为 ikm，任一方被攻破都不足以恢复会话密钥。

服务端 MUST 校验 `timestamp` 在 ±120 秒容差内，且 `cb_hash` 与本连接实际的
TLS Exporter 相等。任一校验失败 → 走 §7 的失败关闭流程。

### 3.2 `ACCEPT`

```
ACCEPT_plain {
    session_id  : 16 bytes
    mode        : u8            // bit0 bare；bit1 记录层用 AES-256-GCM
    path_id     : u32           // 服务端最终采用的路径编号
    ticket_base : u64
    ticket_count: u16           // 默认 1024
    ticket_seed : 32 bytes
    srv_eph     : 1120 bytes     // X25519_pub(32) || MLKEM768_ct(1088) 到客户端临时封装密钥
    server_data : opt bytes
}

ACCEPT.payload = AEAD(k_hs, ACCEPT_plain, ad = transcript)   // nonce = 0…01

ticket_key[i] = HKDF-Expand(ticket_seed, "tide/draft-01 ticket" || u64(id), 32)

ee             = X25519(srv_eph_x_priv, client_eph_x_pub)
                 || MLKEM.Decap(client_eph_dk, srv_eph_ct)   // **必须是混合的**，见下
session_secret = HKDF( ikm = k_hs || ee, salt = session_id, info = "tide/draft-01 session" )
```

只下发一个 32 字节种子而非 1024 把密钥，是为了让 `ACCEPT` 保持小帧——
整批密钥两端各自派生即可。

**`srv_eph` 与 `ee` 是前向保密的唯一来源，MUST 存在，且 `ee` MUST 是混合的
（经典 + 后量子两项都要）。**
客户端的临时公开材料取自 `HELLO.kem_share`（1-RTT：X25519 公钥在最前、临时 ML-KEM
封装密钥在最后）或 `zero_seal.eph`（0-RTT）。
服务端 MUST 为每次握手新生成这两对临时密钥，并在握手结束后 MUST 丢弃私钥。

> 没有它，握手里就**一个服务端临时密钥都没有**：
> `ikm = X25519(客户端临时, 服务端静态) || MLKEM.Decapsulate(服务端静态, ct)`，
> 两项都只依赖长期私钥与线上可见的字节。于是"一份录音 + 事后取得的静态私钥"
> 足以重算 `k_hs`、解开 `ACCEPT`、拿到 `session_id` 与 `ticket_seed`，
> 还原整条会话，连同用那批票据做的所有 0-RTT 会话。
>
> 加上 `ee` 之后，攻击者仍然能重算 `k_hs`（1-RTT 躲不掉：`ACCEPT` 必须在拿到对方
> 临时公钥之前就可读），但缺那把从未上线的临时私钥，`session_secret` 就推不出来。
>
> 因此仍然**不**具备前向保密的是：`HELLO.sealed`、`ACCEPT` 自身、0-RTT 的 `early_data`。
> 这与 TLS 1.3（RFC 8446 §2.3：0-RTT 数据不具前向保密）和 Noise IK
> （`ee` 之前的消息只有弱前向保密）的取舍一致。
>
⚠️ **`ee` 只做 X25519 是不够的**，哪怕 `ikm` 那边已经有 ML-KEM。

> 这一条 draft-01 里写错过一次。`ikm` 的后量子那一半挂在服务端**静态**密钥上，
> `ee` 的经典那一半挂在临时密钥上，两者各自挡住一种敌手，但**交集挡不住**：
>
> | 敌手能力 | `ee` 只有 X25519 | `ee` 是混合的 |
> |---|---|---|
> | 只有量子计算机 | 挡住（`k_hs` 里的 ML-KEM 还在） | 挡住 |
> | 只有静态私钥 | 挡住（`ee` 还在） | 挡住 |
> | **两者都有** | **全部失守** | 挡住 |
>
> 而这是**同一个敌手**：能查抄服务器的国家级对手，正是有能力"先收割后解密"的那一个。
> 把两条威胁分开写，很容易看不见它们的交集。
>
> 因此客户端 MUST 在第一个飞行里发出自己的**临时** ML-KEM 封装密钥，
> 服务端 MUST 对它封装并把密文放进 `srv_eph`。这与 TLS 1.3 的 X25519MLKEM768 同形。
>
> "到**静态**密钥的封装"仍然 MUST 保留：它给的是隐式服务端认证（只有真服务端能解开
> `HELLO.sealed`），是 1-RTT 成立的前提，与前向保密是两件事。两处封装各司其职，缺一不可。

> 代价：`kem_share` +1184、`ACCEPT` +1088、`zero_seal` +1184，
> 多一次 ML-KEM 封装/解封装。**不增加往返，1-RTT 与 0-RTT 的性质都不变。**

`ACCEPT` 的 nonce MUST 与 `HELLO` 的全零 nonce 区分（本规范取 `0…01`）：
同一把 `k_hs` 下重复使用同一个 nonce 会直接泄露明文异或并允许伪造 tag。

服务端 MUST NOT 通告 `bare`，除非外层信道提供 AEAD 且 §5 的信道绑定校验已通过。

### 3.3 `ZERO_RTT`（后续连接，0-RTT）

```
ZERO_RTT {
    version    : u8 = 0x01
    ticket_id  : u64
    nonce      : 12 bytes
    sealed_len : u16
    sealed     : AEAD(ticket_key, zero_seal || early_data,
                      ad = version || ticket_id || nonce)
}

zero_seal {                        // 1293 字节
    cb_hash    : 32 bytes
    timestamp  : u64
    user_id    : 16 bytes
    session_id : 16 bytes
    flags      : u8
    path_id    : u32
    eph        : 1216 bytes        // X25519_pub(32) || MLKEM768_ek(1184)
}

k_hs = HKDF( ikm = ticket_key, salt = cb_hash, info = "tide/draft-01 0rtt" )
```

`zero_seal.eph` 与 1-RTT 里 `kem_share` 前 32 字节起同样的作用：给服务端一把对端临时
公钥去做 §3.2 的 `ee`。0-RTT 路径上没有 `kem_share`，不单独带它的话这条会话就完全
没有前向保密——而 0-RTT 恰恰是长期会话里出现次数最多的那种握手。

服务端处理流程（顺序 MUST 严格保持）：

1. 按 `ticket_id` **只读地**查未消费票据位图，取出票据密钥。
2. 若已消费或超出范围 → **静默丢弃，转入 §7 失败关闭流程**。
   MUST NOT 返回任何区别于掩护站点的响应。
3. 解密 `sealed`。**解密成功即证明对端持有该票据密钥。**
4. 置位（标记消费）。此步 MUST 在解密**成功之后**、且对同一 `ticket_id`
   的并发请求 MUST 原子化（测试并置位是一个不可分割的操作）。
   置位失败（说明并发的另一份先赢了）→ 判为重放，转入 §7。
5. 校验 `cb_hash`、`timestamp`、`user_id` 与票据归属一致。
   **这些检查失败时票据 MUST 保持已消费** —— 对端确实持有密钥，
   这段密文已经上过线，放它回去等于允许重放。

⚠️ **第 4 步 MUST NOT 提前到第 3 步之前。** draft-01 早期版本写的是"置位 MUST 在解密之前"，
那是错的，而且错得足以把 0-RTT 整个废掉。

> `ticket_id` 是**明文**（第 1 步要靠它反查密钥，见下面的鸡生蛋），而本规范又要求
> 票据编号在全局单调空间内分配——两条加在一起意味着 `ticket_id` **完全可预测**。
>
> 于是"先置位再解密"等价于：**任何人**都可以用一个百来字节的伪造帧烧掉任意一张票据，
> 不需要持有任何密钥、不需要嗅探过任何流量。顺着编号数上去，就能把整台服务器上
> 所有用户的票据烧光，使所有人永久退回 1-RTT。而服务端回的还是掩护站点（§7），
> 全程没有任何错误或日志——这正是最难被发现的那种失败。
> 参考实现实测：32 张票据被 32 个垃圾帧烧得一张不剩。
>
> 把置位挪到解密之后**不会**削弱重放保护：原子性由"测试并置位"这一步自己保证，
> 不需要靠"先于解密"来换。并发重放同一份**真实**密文时，所有副本都能解开，
> 但只有一个能置位成功，其余判为重放——正是想要的语义。
>
> RFC 8446 §8.2 对 TLS 1.3 的 0-RTT 给的是同一个顺序：服务端**先验 PSK binder**
> （证明持有 PSK），之后才去查防重放记录。

票据 MUST 在签发后 24 小时过期，即使未被消费。

> **鸡生蛋**：第 1 步要查位图就得先知道用户，而 `user_id` 在待解密的密文里。
> 本规范的解法是要求票据编号在**全局单调**空间内分配，于是 `ticket_id` 本身
> 唯一确定所属批次（连带用户）。集群实现要么复制这个性质（全局单调发号），
> 要么把 `user_id` 明文放进 `ZERO_RTT`——后者泄露用户标识，MUST NOT。

> **多节点部署警告**：位图是**服务端硬状态**。若同一用户可能落在不同节点上，
> 位图必须共享，否则重放保护在节点间失效——攻击者只需把重放流量投给另一个节点。
> 这是本协议唯一显著增加运维负担的地方。见 §12.1。
>
> 共享位图的实现 MUST 同时提供**只读查询**与**原子测试并置位**两个操作，
> 而不能只提供一个合并的"查并消费"。只有合并接口的话，上面第 1 步就不得不
> 提前消费，那条烧票据的路径就又回来了。

## 4. 流

### 4.1 `STREAM_OPEN`

```
payload {
    kind        : u8        // 0 = TCP 流；1 = UDP 关联
    recv_window : varint    // 本端初始接收窗口
    addr        : SOCKS5 地址格式（ATYP + ADDR + PORT）
}
```

接收方 MUST 幂等处理重复的 `STREAM_OPEN`（相同 `stream_id` 视为同一条流）——
重连后发送方会补发它，见 §9。

流号 MUST 奇偶分家：客户端用奇数、服务端用偶数。两端因此可以同时开流而无需协商。

**`kind=1` 的 UDP 关联同样是流，MUST 计入并发流上限**，两个方向都算——本端主动开的
和对端开进来的。这一条写出来是因为它太容易只在"开 TCP 流"那条代码路径上实现：
UDP 关联另有一条自己的入口，漏掉之后上限可以被 UDP 完整绕开，而每条关联还各自带着
一个收队列（§9.3），于是"关联数无界"乘上"每条队列有界"仍然无界。

接收方 SHOULD 在建流后立刻回一个 `STREAM_ACK` 通告真实窗口。
在收到它之前，发送方 MUST NOT 发送超过 64 KiB。

### 4.2 `STREAM_DATA`

```
payload { offset : varint,  data : bytes }
```

`offset` 是该流发送方向上的**绝对字节偏移**，从 0 开始。

> ★ 这是 draft-01 相对 draft-00 最重要的一处改动，也是"路径死掉而连接不断"的全部机理。
>
> 底层 TCP/QUIC 已经是可靠的，但"可靠"是**每条路径**的属性，而会话要活得比路径长。
> 路径断掉的那一刻，已被内核 ACK、但尚未抵达对端**应用层**的字节全部消失，
> 且本端无从知道丢了哪些——TCP 的 ACK 只保证到达内核，不保证到达对端应用。
> 没有会话级的绝对偏移，一次 Wi-Fi 切换就会让每条流中间凭空少掉一段，
> 表现为"网页加载到一半卡住"或"下载文件校验和不对"，**且不会有任何报错**。
>
> 有了绝对偏移，重发就是幂等的：接收方丢弃 `offset + len ≤ recv_offset` 的重复段，
> 缓存 `offset > recv_offset` 的乱序段，于是发送方可以无脑地从最后确认点整段重来。

接收方：
- `offset + len ≤ recv_offset` → MUST 丢弃（迁移后的正常重复）。
- `offset > recv_offset` → MAY 缓存至乱序缓冲；缓冲量超过接收窗口时 MUST 丢弃，
  由发送方重传。缓冲无上界是内存炸弹，而重传的代价有界。
- 否则取尾部有用段，推进 `recv_offset`，并尝试排空乱序缓冲。

⚠️ **乱序缓冲的计量 MUST 包含每段的固定开销，不能只累加载荷字节。**

> 这条看起来像实现细节，其实是上一条 MUST 成不成立的前提。"缓冲量超过接收窗口"
> 里的"缓冲量"如果只数载荷，那么段越小，这个数与真实内存占用的偏差越大——
> 每段都要付一份索引结构 + 切片头 + 一次独立的小块堆分配，**与段长无关**。
>
> 实测（Go 1.26 / amd64，窗口 512 KiB）：每段固定开销约 80 字节，于是
>
> | 段长 | 段数 | 记账值 | 真实堆占用 | 放大 |
> |---:|---:|---:|---:|---:|
> | 1 B | 524288 | 512 KiB | **42.5 MB** | **81×** |
> | 8 B | 65536 | 512 KiB | 5.8 MB | 11× |
> | 64 B | 8192 | 512 KiB | 1.2 MB | 2.2× |
> | 1024 B | 512 | 512 KiB | 0.54 MB | 1.1× |
>
> 攻击方式完全落在协议允许的范围内：把 `STREAM_DATA` 拆成 1 字节一段、
> 段间留一个字节的空洞让它永远接不上。乘上并发流上限（实现默认 1024）就是几十 GB。
> 把固定开销计入之后，同样的输入实占降到 300 KB，**真正落在窗口之内**。
>
> 代价可以忽略：真实的乱序段是 MTU 量级（~1400 字节），80 字节的记账开销是 5.7%。
>
> 同一条推论适用于**任何按对端输入增长的缓冲**——§9.2 的抢跑数据报暂存区
> 因此除了字节上界还必须有条数上界。上界限错了量，等于没有上界。

### 4.3 `STREAM_ACK`

```
payload { ack_offset : varint,  max_offset : varint }
```

- `ack_offset`：已**连续**收到的偏移（累积确认）。累积语义使 ACK 丢失可自愈——
  下一个 ACK 覆盖前一个，不需要重传 ACK。
- `max_offset`：允许对端发送到的上界 = `ack_offset + 剩余缓冲`。
  应用读得慢会自然把窗口压小，反压一路传回发送端。

发送方 MUST NOT 使 `send_offset` 超过 `max_offset`，
且 MUST 将未确认字节 `[ack_offset, send_offset)` 保留在重传缓冲中，上限即流窗口。

接收方 SHOULD 在累积 32 KiB 或收到 `STREAM_FIN` 时发送 `STREAM_ACK`。

### 4.4 重传超时（RTO）

发送方 MUST 维护一个兜底重传定时器：若某条流存在未确认字节、且超过一个 RTO
（SHOULD 取 `clamp(2×min(path SRTT) + 200ms, 500ms, 4s)`）没有任何确认进展，
则 MUST 把待发指针回退到 `ack_offset` 并重发。

> 路径健康检查看的是**路径**，而丢帧可以在路径完全健康时发生——比如 `STREAM_OPEN`
> 恰好落在路径断掉的那一刻，或对端因流表满而丢弃了帧。没有 RTO，这类情况表现为
> 一条永远卡住的连接，且两端都认为自己没问题。这是弱网下最难查的一类故障。

## 5. 信道绑定

```
cb_hash = TLS-Exporter( label   = "tide-channel-binding",
                        context = empty,
                        length  = 32 )
```

QUIC 路径使用 QUIC-TLS 的等价导出器。若某传输**无法**提供导出器，
实现 MUST 在该传输上失败关闭，MUST NOT 跳过信道绑定继续——
悄悄跳过一个安全属性，没人会发现它已经没了。

客户端 MUST 将 `cb_hash` 纳入 `sealed_auth`（§3.1）或 `sealed`（§3.3）的被认证数据；
服务端 MUST 独立计算并比对。不匹配 → 失败关闭，MUST NOT 降级重试。

此机制使任何终止并重建外层 TLS 的中间实体（企业 MITM CA、CDN 回源、透明代理）
都无法完成握手，同时是启用 `bare` 模式的前提。

## 6. 记录层与模式

### 6.1 `sealed`

```
record = u16 ct_len || AEAD(k_path, frames…, ad = u16 ct_len)
nonce  = 4 个零字节 || u64 大端序号（每路径独立自增）
```

AD 绑定长度前缀：否则攻击者可以改前缀把一条记录切成两条，AEAD 本身察觉不到。

明文按**批**封装（一批可含多个帧），而非每帧一封。交互阶段一批就是一帧、没有损失；
批量阶段一批装满 MTU，16 字节 tag 摊到 16 KiB 上是 0.1%。

密钥按方向再按路径分叉：

```
secret   = HKDF( k_hs, salt = session_id, info = "tide/draft-01 session" )
k_c2s    = HKDF-Expand(secret, "tide/draft-01 c2s", 32)
k_s2c    = HKDF-Expand(secret, "tide/draft-01 s2c", 32)
k_path   = HKDF-Expand(k_dir, "tide/draft-01 path" || u32(path_id), 32)
```

> ★ 按路径分叉是多路径正确性的硬要求，不是洁癖。AEAD 的 nonce 就是序号，
> 而两条路径各自独立发送，序号必然会撞。共用一把密钥就会出现 (key, nonce) 复用——
> 对 ChaCha20-Poly1305 和 GCM 都是灾难性的。分叉之后序号只需在路径内唯一，
> 迁移时也不必同步任何计数器。

### 6.2 `bare`

内层不加密，帧直接落在外层 TLS/QUIC 记录里。安全性完全由外层承担，
前提是 §5 的信道绑定已**密码学地**证明外层未被中间人替换。

`bare` 模式 MUST 关闭填充：要插填充就得在用户态碰载荷，而 `bare` 的全部意义
就是让用户态不碰载荷（从而 kTLS/`splice()` 可用）。

## 7. 失败关闭

任何认证失败（`sealed_auth` 校验失败、`cb_hash` 不匹配、票据已消费、时间戳超窗、
版本不支持）时，服务端：

1. MUST NOT 返回任何 TIDE 帧或错误指示。
2. MUST 将该连接**已接收和后续全部字节**原样代理至掩护源站，直至任一端关闭连接。
3. MUST NOT 对该路径做特殊的超时、限速或日志分支处理。

> **关键**：不能"模拟"掩护站点的响应，必须**真的转发**。若认证失败路径耗时 0.1ms
> 而真实站点路径耗时 50ms，探测方只需测量响应时间分布即可区分两者。
> **时序是这里唯一真正难伪造的东西。** 掩护源站 MUST 真实可达且延迟合理（同机房或本机）。

### 7.1 判定必须**尽早**

服务端 MUST 在能够判定"这不是 TIDE"的**最早时刻**转入失败关闭，具体地：

- 读到 `type` 字节后，若不属于 `{HELLO, ZERO_RTT}` → 立即失败关闭。
- 读到 `length` 后，若超出该类型的合理范围 → 立即失败关闭。
- 握手帧的读取超时 SHOULD ≤ 5 秒。合法客户端在外层握手完成后立刻发出整个握手帧，
  一个 RTT 都不等。

> 这一节是实现时补的，因为最初的实现"读完整帧再判"直接把伪装作废了：
> 探测方发一个 HTTP 请求过来，`GET /…` 被当成一个声称长度 5152 字节的帧，
> 服务端一直等到读超时（15 秒）才转发，而真实站点毫秒级就回。
> 只看 2 个字节就能否掉绝大多数探测——HTTP 以 `G`/`P`/`H` 开头，
> TLS-in-TLS 以 `0x16` 开头，端口扫描往往一个字节都不发。

### 7.3 失败关闭的**时刻**不得取决于探测方发了什么

服务端 SHOULD 在读取任何字节**之前**就发起到掩护源站的连接。

⚠️ 但 MUST NOT 在确认握手失败**之前**把任何字节推给掩护源站。

> §7.1 要求尽早判定，这在时序上留下一个副作用：不同探测在不同深度出局，
> 而"出局深度"直接写进了"多久之后掩护源站开始回话"。一个 HTTP 请求第 2 个字节
> 就被否掉；一个长得像 `HELLO` 的探测要等服务端做完 KEM 解封装才在 AEAD 上失败。
>
> 这是个**自足**判据：探测方不需要任何对照基线，同一台机器自己跟自己比就行，
> 而真实源站对这两个输入没有任何时间差。参考实现实测（掩护源站在本机、
> 两种探测长度对齐）：不做任何处理时 182µs vs 315µs（**+73%**，Welch t = 38.7）；
> 提前拨号之后降到约 +33%。
>
> ⚠️ 提前**推请求**试过，一无所得：加上它差值纹丝不动（64.1µs → 64.1µs）。
> 原因不难想——掩护源站的**响应**在确认握手失败之前本来就不能回给客户端，
> 请求提前送出去并不能让响应提前到达。而代价是实在的：那样每一条**合法**握手
> 都会把加密后的握手帧推给掩护源站，于是掩护源站为每次正常连接记一条畸形请求日志，
> 谁能看到那份日志就能数出握手次数；掩护源站若是第三方站点，还等于替用户
> 往别人服务器上发垃圾。既有实践（Xray/Trojan 的 fallback）同样是**只有认证失败
> 才碰后端**。所以这里是 MUST NOT，不是 SHOULD。
>
> ⚠️ 这条 SHOULD **不能**把差值消到零：掩护源站的字节在确认握手失败之前绝不能
> 回给客户端，所以任何走到密码学那一步的探测都必然要等它。
> 两条"彻底"的路都更糟——对所有输入都做一遍 KEM 会把一个几字节的探测变成一次
> 公钥运算（§12.4 里同一类放大），加固定响应下限则让所有畸形请求恰好耗时 T。
> 本规范因此只要求把**可以并行的部分并行掉**，并要求实现把残留量测出来、记下来。

### 7.2 掩护源站不可达

若掩护源站连不上，服务端 MUST 保持连接并读到对端放弃，MUST NOT 立即关闭——
立即关闭是一个可测量的、与真实站点截然不同的行为。

## 8. 多路径与调度

- 会话可同时绑定多条路径。每条路径独立完成 §3 握手，并在 `auth_plain.session_id`
  中携带已有会话号以加入现有会话。
- 调度器 SHOULD 默认自 TCP 路径起步，后台建立 QUIC 路径。
- QUIC 路径探测失败（UDP 被封锁）时，MUST 静默全量回落 TCP，不得向用户暴露错误。
- 单条流的帧 SHOULD 保持路径亲和，以避免跨路径乱序开销。
- 拥塞控制每路径独立。MUST NOT 默认启用无上界的激进拥塞控制。
- **同一会话内 `path_id` MUST 唯一。** 接收方 MUST NOT 接纳一条 `path_id` 与本会话
  现有路径重复的新路径；对端报上来的号已被占用时，服务端 SHOULD 在 `ACCEPT` 里
  改派一个未被使用的号（客户端 MUST 以 `ACCEPT` 里的号为准）。

> 这不是编号整洁问题，是**密钥问题**。记录层密钥是 `pathKey(方向密钥, path_id)`，
> 只由 `path_id` 决定；而每条路径的记录序号都从 0 起。两条路径共用一个 `path_id`
> 就是同一把密钥配同一串 nonce——AEAD 当场失效：两段密文异或即泄露明文，
> Poly1305 的认证密钥也跟着复用，伪造随之成立。
>
> 而 `path_id` 是**对端报上来的**（`auth_plain.path_id`），属于典型的
> "拿对端可控的值去派生密钥"，因此唯一性 MUST 由接收方强制，
> 不能指望对端自觉。参考实现从前直接照单全收，只在对方给 0 时才自己分配；
> 更微妙的是它的客户端注释一直写着"服务端可能给了不同的 path_id（本端选的号已被占用）"
> ——两边都按"服务端会换号"来写，而服务端并没有做。
>
> 检查 MUST 与"把路径挂进会话"这一步**原子地**完成，否则并发加入能绕过它。
> 多路径 QUIC 给的是同一条要求、同一个理由："为保证 nonce 唯一，
> path ID 不得在同一条连接内被另一条路径复用"（`draft-ietf-quic-multipath`）；
> 它把 path ID 拌进 nonce，本协议拌进密钥，而"同一连接内不得复用"完全一样。

- **单条会话绑定的路径数 MUST 有上界。** 加入路径这件事由对端驱动：任何持有有效
  `session_id` 的对端都能不断握手加进来，而每条路径都要占住独立的收发资源，
  并让"给这一帧挑一条路"的代价随路径数线性上升。
- **新路径加入时 MUST NOT 无条件重发所有未确认字节**，仅当会话此刻**一条可用路径都没有**
  （即这是一次重连恢复）才允许全量退回重发。
- **单个用户同时持有的会话数 MUST 有上界**，且判定 MUST 在服务端发出 `ACCEPT` **之前**完成。
  超出上界时，实现 MUST 优先淘汰**当前一条路径都没有**（即正处于 §9 宽限期）的会话，
  取其中最早失去路径的那条；若全部会话都还有活跃路径，则 MUST 拒绝新会话，
  **MUST NOT** 淘汰任何仍有路径的会话。

> 会话曾经是本协议里唯一没有上界的一级——路径有（上一条）、流有（§4.1）、
> 票据批次有（§12.4）——而它和那三个是**同一个形状：由对端驱动**。
> 一次握手建一条会话，每条会话要占住流表、路径表、若干常驻执行单元和一个宽限期
> 定时器；而关键在于会话**在路径全断之后还要活满宽限期**（§9，实现默认 120 秒）。
> 那正是它存在的理由，也正是它可以被拿来堆积的原因：握手、断开、再握手，
> 一个**已认证**的对端就能让服务端替它攒下成千上万条"正在等主人回来"的会话，
> 全程不触发任何错误路径。这正是 RFC 9000 §21.9（Peer Denial of Service）
> 描述的那一类：处理开销与状态变化相对带宽不成比例。
> 实测负对照（上界设为 4）：不加限制时同一用户攒到 **21 条**仍在线性增长。
>
> ⚠️ **淘汰顺序比上界本身更容易写错，而写错的两种方式都很贵：**
>
> - 直接拒绝新会话 → 把**恢复路径**堵死。一个正常重连的客户端，本来就会在旧会话
>   还停在宽限期里的时候建一条新的（§9），那恰恰是这个协议存在的意义。
> - 不区分在用与闲置、按时间挑最老的淘汰 → 上界本身**变成针对真实用户的攻击面**：
>   谁都能靠反复握手把别人正在用的连接挤掉。实测负对照里这条一击即中。
>
> 宽限期里的会话此刻没有在服务任何人，淘汰它的代价上限是少一次无缝恢复。
>
> 判定必须在 `ACCEPT` 之前，是为了让拒绝走**与其它认证失败完全相同**的那条路
> （§7 失败关闭 → 掩护源站）。放在 `ACCEPT` 之后拒绝，客户端已经认为握手成功，
> 接着会把掩护源站的字节当作 TIDE 帧来解——既多出一个可测量的差异，
> 又让合法客户端的失败变得无从诊断。

> 后面这条看着像优化，其实两头都是坑。
>
> 正确性一侧：数据还在一条健康的路径上飞，接收方又按绝对偏移去重（§4.2），
> 所以重发的字节从头到尾没有产生任何效果，纯粹是白烧带宽与对端的乱序缓冲。
> 正常的多路径爬坡（TCP 起来之后后台再加 QUIC）每次都会踩到。
>
> 安全一侧更要紧：既然加路径由对端驱动，"加一条路径"就成了一个**放大杠杆**——
> 一次廉价的加入握手可以逼出最坏 `MaxStreams × StreamWindow` 的出向流量
> （实现默认 1024 × 512 KiB ≈ 512 MB），外加每条流一个执行单元。
> 反复加入即可把发送方的出口打满，而全程没有任何错误路径被触发。
>
> "某条路径死了但还有别的活着"不需要全量重发：那时只需恢复**钉在那条死路径上的流**，
> 这是 §8.2 状态机本来就该做的事，范围精确得多。
>
> 多路径 QUIC 的取向是一样的：在确认丢失或路径被判死之前不重传，正是为了躲开这种
> 虚假重传（`draft-ietf-quic-multipath`）。

### 8.0 收帧的那条执行流 MUST NOT 阻塞在发送上

处理收到的帧的那条执行流（读循环）**MUST NOT** 因为发送一帧而阻塞。
读循环里产生的所有出向帧（`STREAM_ACK`、拒绝流的 `STREAM_RST`、补票信号等）
MUST 经由不施加反压的机制交给别的执行流去发。

> 违反它的后果是**整条会话彻底卡死，两端对称，无人报错**：
>
> ```
> 发送方 pump 拿着某条流的写锁，堵在流控里等对端开窗；
> 读循环收到该流的 FIN，要回 ACK，去抢同一把写锁，堵住；
> 而对端要开窗，恰恰得靠这个读循环继续把数据读走。
> ```
>
> 这不是理论推演。本实现里它把一个用例卡了 **9 分 33 秒**，直到 10 分钟的测试超时
> 才暴露；那个用例单独跑只要 0.42 秒——也就是说它只在别的用例把负载堆上去之后
> 才出现，正是最容易被误判成"偶发红"的形状。
>
> 触发它的根源是**两条数据面的形状不一致**：可靠流那条把帧追加进批量缓冲、由独立的
> 写协程下发，所以从不阻塞；QUIC 分流那条却在持锁的情况下直接调底层流的 `Write`。
> 同一个发送入口，一条路径上不阻塞、另一条阻塞——调用方按前者的直觉写，就中招。
> 因此这条要求写在**协议层**而不是某个实现的注释里：只要"读循环里回一帧"这件事
> 存在，它就得成立。
>
> 处置是成熟做法。Go 官方 `net/http2` 服务端的原则是"serve 协程绝不阻塞在写上"——
> 它的 `writeFrame` 排一帧就返回、不施加反压，真正等在线上的是 handler 而不是
> serve 协程；从 handler 发帧则另有 `writeFrameFromHandler` 走通道，
> 正是为了避开同一个死锁。
>
> ⚠️ 把这些帧交出去时**MUST NOT 让不同流共用同一条发送执行流**。
> 共用一条的话，一条卡在流控里的流会把其它所有流的 `STREAM_ACK` 一起压住——
> 这正是 §12.5 花力气消除的队头阻塞（每条 TIDE 流一条独立 QUIC 流），
> 在发送侧原样重建一遍就白分了。修这个死锁时第一版就是共用的，两轮全量验证全绿，
> 因为**没有任何测试会在一条流被流控卡住的同时去量另一条流的 ACK 延迟**。
>
> 合并是免费的额外收益：`STREAM_ACK` 是累积量，同一条流待发多个时只需要发最新的
> 那一个，并发发出两个也无害。而一次性的控制帧（如拒绝流的 `RST`）队列满时
> MAY 直接丢弃——丢一个 `RST` 只是让对端多等一个超时，
> 为了发它把读循环堵住则要赔上整条会话。

### 8.1 迁移判据 —— 用相对评分，**不要**用丢包率

调度器 SHOULD 周期性（约 2 秒）比较各路径评分，把流迁到最好的那条。
**"最好"MUST 是针对该流评的**，不能取一条全局最优路径再把所有流都塞过去——
批量流与交互流对路径的偏好本来就不同，一个全局最优抹掉的正是这个区别。

> 参考实现在这一点上曾经三处各说各话，而且是**周期性的那一处赢**：
> 路径降级时只迁批量流（交互流留在 TCP），建流时给批量流偏 QUIC、交互流偏 TCP，
> 但每 2 秒一次的重平衡取一条全局最优、把所有流都迁过去，两种偏好都不看。
> 前两处的判断活不过一个重平衡周期。
>
> ⚠️ 影响要说准：偏好是 ±20% 量级，而迁移门槛是 2 倍，所以偏好挪动的是**触发点**
> 而不是结论——交互流迁往 QUIC 的条件从"另一条差 2 倍"变成"差 2.5 倍"。
> 交互流并不会被随便赶走，只是比设计意图早 25% 被赶走；代价是每迁一条都要
> 重发未确认字节。把偏好收成一个所有调度点共用的函数，这个矛盾从结构上消失。
判据 SHOULD 为：

```
score = SRTT_ms + 2 × RTTVAR_ms + loss × 2000
迁移条件：best.score × 2 < current.score，且连续 2 次观测都成立
```

> ★ **draft-00 §8 那条"TCP 路径丢包率持续超过 2% 时迁移"是错的，按字面实现永远不会触发。**
>
> `PATH_PROBE` 走在 TCP 连接内部，丢掉的段由内核重传，探测最终**总会**到达，
> 只是变慢。所以应用层测到的 TCP 丢包率恒为 0——丢包在 TCP 上不表现为丢包，
> 表现为 RTT 膨胀与队头阻塞。
>
> 实测（树莓派 5 ↔ x86，netem 5% 丢包，见 §11.3）：同一时刻 TCP 路径报
> `loss=0.00% / srtt=44.69ms`，并存的 QUIC 路径 `srtt=1.26ms`。
> 按丢包率写的判据一次都没触发，QUIC 路径建起来了却只拿到 0.1 MiB，
> 而 TCP 扛了 52.2 MiB。改成按评分迁移后，p90 从 187ms 降到 9ms。
>
> 两个门槛都是必需的：**2 倍**保证只有显著差距才值得付迁移的代价（未确认字节要重发、
> 两条路径的拥塞窗口都要重新长起来）；**连续 2 次**保证不被一次抖动骗到。
> 没有滞回的实现会在阈值附近每秒来回迁移几十次，比不迁移还糟。

### 8.2 路径健康状态机

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `active` | 正常 | 连续 3 次探测成功且丢包估计 ≤ 2% |
| `degraded` | 仍可用，但该让出批量流 | 丢包估计 > 2% |
| `suspect` | 新流不再选它 | 连续丢失 2 个探测 |
| `dead` | 流全部撤离 | 连续丢失 4 个探测，**或**静默超过 8 秒 |

- 探测超时 SHOULD 取 `max(3×SRTT + 4×RTTVAR, 2s)`。下界是为了不误杀高延迟线路——
  卫星/跨洲链路 RTT 600ms 是正常的，用固定 2 秒判丢会让它一直处于"丢包 100%"的假象里。
- **静默计时器是独立于探测的第二个死亡判据，MUST 实现。** 探测的往返依赖对端还在响应；
  若对端进程活着但会话状态已丢（如服务端重启），探测可能仍被回复，而流数据永远不来。
  静默计时器不看语义，只看物理层面有没有字节，是更硬的证据。
- 已判 `dead` 的路径 MUST NOT 复活：会话侧的流已经撤离，复活会造成两条路径同时认领同一批流。

### 8.3 每路径独立的填充调度

填充阶段计数器 MUST 是**每路径**的，不是每会话的。

**填充 MUST 与 `bare` 无关。** `bare`（§6.2）只表示"用户态不做 AEAD"，
与要不要插填充是两件独立的事；QUIC 路径恒为 `bare`，把两者绑在一起等于让
QUIC 路径完全裸奔——而 §8.1 恰恰把批量流往 QUIC 上偏，那是承载字节最多的一条路。

> 参考实现踩过这个：`bare` 分支里顺手关掉了填充，理由写的是"要插填充就得在用户态
> 碰载荷，那 `splice()` 就没了"。这个理由后来被 §12.3 否掉了（多路复用协议必须解帧，
> 解帧就必须把数据读进用户态，`splice()` 无从谈起），但那个开关一直开着——
> 一个为**已被否决的优化**让路的取舍，比没做过还危险，因为它看起来是有意为之。
>
> 学界对 QUIC 的网站指纹攻击只要 40 个包就能到 95% 以上准确率，包长是主要特征之一
> （见 *Website Fingerprinting on Early QUIC Traffic*）。QUIC 自己的 `PADDING` 帧
> 存在的理由与这里完全一样。
>
> 代价可忽略：填充预算本来就只花在判决窗口。参考实现实测，QUIC 路径上
> 20 次 100 字节往返在判决窗口内发出 27516 字节（裸载荷 2160），
> 而批量阶段 16×8 KiB 只多用 187 字节（**0.14%**）。前重后轻的预算设计正是为此。

> 分类器观察的是一条 TCP/QUIC 连接。会话迁移到新路径后，新路径在观察者眼里
> 就是一条全新的连接，必须重新走一遍判决窗口。沿用会话级计数器会让迁移后的
> 新连接直接以"批量、零填充"开场——正常 HTTPS 连接不会一上来就发满 MTU 的定长包，
> 那是个极其显眼的特征。网络波动越频繁、迁移越多，这一点越重要。

### 8.4 握手帧 MUST 填充

`HELLO`、`ZERO_RTT`、`ACCEPT` 三个帧的线上长度 MUST NOT 是常量。
实现 MUST 给它们加随机填充，填充量 SHOULD 取自密码学随机源。

> **这是整份规范里最便宜的一个指纹，而 §8.3 完全覆盖不到它。**
>
> 这三个帧的长度**完全由协议结构决定**——`HELLO = 1 + kem_share + client_random
> + 2 + sealed`，每一项都是定长——所以不填充的话，每条 TIDE 连接的第一条应用记录
> 都是**同一个数**，与用户、时间、内容都无关。
> DPI 只要问一句"TLS 握手之后的第一条应用记录是不是恰好 N 字节"就完事了：
> 一个包，不需要观察时序，不需要统计，不需要基线。
>
> §8.3 的判决窗口救不了它：那套填充从**握手之后**才开始，而握手帧不经过填充调度器。
> 参考实现实测：不填充时 `HELLO` 恒为 2437 字节、`ZERO_RTT` 恒为 1337、`ACCEPT` 恒为 1204。
>
> ⚠️ 填充量**不建议**照搬 §8.3 那张 HTTPS 分布表。握手帧已经 2.4 KB
> （后量子的临时封装密钥，§3.1），分布里能装下它的只剩几个尾部桶，
> 按质量采样出来的均值是 6.6 KB——每次握手平均多花 4.2 KB，
> 且约 1/5 的握手会发出一条 11–16 KB 的记录，那本身比 2.5 KB 更不像正常流量。
> 要消掉的是"**恒等于**某个值"，不是把它挪到分布的另一个稀疏角落。
> 参考实现取的是"均匀展宽 4 KiB"：常量没了，开销有上界，
> 长度仍落在真实存在的桶里。

### 8.5 时序：周期性心跳 MUST 抖动

任何周期性发送（`PATH_PROBE`、保活）的间隔 MUST 加入随机抖动，
实现 SHOULD 取标称值的 ±40%。判决窗口内，实现 SHOULD 在**静默间隔**里
以低概率插入 `PADDING` 帧，长度取自 §8.3 同一张分布表。

**"周期性发送"包括周期性的重连尝试。** 补一条冗余路径失败后的重拨 MUST 退避
（SHOULD 指数退避并封顶），且间隔同样 MUST 抖动。

> 这一条本来就在上面那句话的字面范围里，单独点出来是因为参考实现漏了它：
> 补不上第二条路径时，重拨是**固定 2.000 秒**，既不退避也不抖动。
> 它比这一节当初要治的 `PATH_PROBE` 节拍器更显眼——每一拍都是一次完整的
> TCP+TLS 拨号，链路上任何观察者都能看见一串等间隔的新连接，
> 而识别它连机器学习都不需要。
>
> 退避的理由则是另一件事，两条互不替代：波动往往是整片网络的，
> 大量客户端会在同一时刻失去第二条路径，然后以完全相同的节奏一起重拨，
> 把刚要恢复的链路再打垮一次。**退避降低总量，抖动打断同步**，缺一不可
> （AWS *Exponential Backoff And Jitter* 讲的就是这个分工）。
>
> 讽刺的是这两条道理在参考实现里各写过一遍——重连恢复循环的退避注释讲的是惊群，
> QUIC 探测循环的注释讲的是"一串规律的探测本身就是个特征"——唯独冗余路径这条漏了，
> 而它恰恰是文档里专门推荐给移动网络的开关，也就是最容易反复补不上的场景。

> **长度和时序是两个彼此独立的维度，把长度修得再像也不会让时序变像。**
>
> 固定周期是所有时序特征里最便宜、最不该留的一个：识别它连机器学习都用不上，
> 对到达间隔做个直方图，或者一次自相关，就一眼看穿。
> 参考实现在补这条之前，一条应用层完全静默的连接，线上包的到达间隔实测为
> **均值 1000.2ms、标准差 0.15ms、变异系数 0.00015**——精确到 0.15 毫秒的节拍器。
> 加上 ±40% 抖动与判决窗口心跳之后，同样的测量变成变异系数 **0.69**。
>
> 抖动保持均值不变，所以 §8.2 的路径死亡检测时延基本不受影响（最坏晚 0.4 个间隔）。
>
> 这一条**不能**根治网站指纹攻击——那需要恒定速率掩护流量，与低延迟目标直接冲突，
> 见 design.md §10。它消除的只是"这条连接上挂着一个节拍器"这种不该存在的免费特征。
> 学术上这类做法叫 adaptive padding（WTF-PAD 与 Tor 的 circuit padding 框架都基于它）。

## 9. 会话存活与重连

- 会话在**一条路径都没有**的情况下 MUST 继续存在至少 `SessionGrace`（默认 120 秒）。
  服务端在此期间 MUST 保留流状态、未确认字节与上游连接。
- 客户端在失去全部路径后 SHOULD 以指数退避 + 抖动重拨，并携带原 `session_id` 加入。
  退避 SHOULD 上限 5 秒；抖动是必需的——波动往往是整片网络的，
  几十个客户端同时重连会把刚恢复的链路再打垮一次。
- 新路径接入后，发送方 MUST 对每条流：
  1. 若 `STREAM_OPEN` 尚未被对端确认（未收到该流的任何帧），先补发 `STREAM_OPEN`；
  2. 将待发指针回退到 `ack_offset`，重发未确认段；
  3. 若已发过 `STREAM_FIN`，补发之。
- 服务端若不认识客户端声称的 `session_id`（宽限期已过或服务端重启），
  MUST 当作新会话建立并在 `ACCEPT` 中返回新的 `session_id`，
  MUST NOT 失败关闭——这不是攻击，是正常超时。客户端据此放弃旧会话。
- 宽限期耗尽后，会话 MUST 干净地失败（向上层报错），MUST NOT 无限挂起。

### 9.1 UDP 不重传

`DATAGRAM` MUST NOT 进入重传缓冲。UDP 本就不可靠，给它加可靠性会改变上层协议
（QUIC、DNS、游戏）自己的拥塞与超时行为，通常比丢包更糟。
路径切换期间丢掉的数据报就是丢了——这与在真实网络上丢包没有区别。

### 9.2 抢跑的 `DATAGRAM`

收到 `DATAGRAM` 而 `stream_id` 对应的关联尚未建立时，接收方 MUST NOT 因此失败关闭，
且 SHOULD 在**一个 RTT 量级**内暂存该数据报、待关联建立后按原序交付；
暂存 MUST 有上界，超界时 MUST 丢弃而不是扩容。**字节上界与条数上界缺一不可**
（理由同 §4.2 末尾那条：只限字节的话，对端拿 1 字节的数据报配上各不相同的
`stream_id`，就能用很小的记账额度换到大得多的真实占用）。

> 这不是罕见竞态，而是必然：`DATAGRAM` 走不可靠数据面，`STREAM_OPEN` 走可靠流，
> 两者之间**没有任何顺序关系**——数据报不排队、不等流控、不等重传。
> 因此在任何有 RTT 的链路上，"一条 UDP 关联的第一个数据报比它自己的 `STREAM_OPEN`
> 先到"是常态。直接丢弃是合法的（见下），但代价隐形：DNS 的第一个查询消失、
> 应用等自己的重传超时（通常 1 秒）；被代理的 QUIC 少一个 Initial、握手退避一轮。
> 两者都不报错，只表现为"每开一个新 UDP 连接就卡一下"。
>
> RFC 9297 §5.2 对完全同构的问题（收到的 HTTP Datagram 其 Quarter Stream ID 指向
> 一条尚未创建的流）给出的处置正是这两选一：静默丢弃，或在一个往返量级内暂存等待。
> 本文取后者并加上界——上界不是洁癖：没有它，对端只要对不存在的 `stream_id`
> 持续发 `DATAGRAM`，就能在完全合法的前提下让接收方无限占用内存。

### 9.3 已建关联的收队列

关联建立**之后**的收队列同样 MUST 有上界，且同样是**字节与条数两个上界缺一不可**；
超界时 MUST 丢弃最老的而不是扩容（陈旧的 UDP 数据报比新到的更没价值）。
此外，一个端点为**整条会话**的所有关联加起来所缓冲的数据报字节数 MUST 有上界。

> 三个上界各挡一类，少任何一个都留一个完整的洞：
>
> **只限条数挡不住大数据报。** 单条 `DATAGRAM` 的载荷上限是 `MaxFrameBody - 300`
> ≈ 56 KiB，队列限 512 条就是 28 MiB——**一条**关联。实网里 UDP 数据报几乎都在
> 1500 字节以内，所以正常流量永远碰不到这个数，测试也就永远绿。
> 参考实现在这一点上分成两派，而分歧的根源正是单条上限：quic-go 只限条数
> （`maxDatagramRcvQueueLen = 128`），因为 QUIC 的 `max_datagram_frame_size` 把
> 单条压在 ~1200 字节，条数与字节本来就是同一个量；.NET / MsQuic 的
> `DatagramReceiveQueueLength` 则明确定义为"缓冲入向数据报所用的**字节**数"。
> 本协议的单条上限属于后者。
>
> **只限字节挡不住小数据报。** 每条排队记录除载荷外还有 slice 表项与结构体，
> 合计上百字节且与载荷长度无关。LSQUIC 的 QUIC-LEAK（CVE-2025-54939）正是栽在
> 这个量上：每个包约 96 字节的结构体，一条 UDP 数据报换约 960 字节 RAM，
> 内存以带宽 70% 的速度线性增长。这与 §4.2 末尾那条是同一个道理。
>
> **只限单关联挡不住多关联。** 关联数受 §8 的流数上限约束，但"每条有界"乘以
> "条数有界"仍是个大数（1024 × 256 KiB = 256 MiB）。这是本协议实现里反复出现的
> 一类错误——两个各自正确的上界合起来并不构成一个可接受的上界——所以再加一道
> 全会话硬顶。全会话预算耗尽时丢**新**的（此时丢谁都是丢，丢新的不打乱已排好的
> 顺序）；本关联自身的两个上界则丢**最老**的，这保证一条正在收数据的关联
> 总能回收自己的额度，不会被别的关联饿死。

> ⚠️ 关联被摘掉（对端 `STREAM_RST`、或流被回收）时，实现 MUST 把它收队列里的
> 字节从全会话预算中归还。漏了这一步的两个后果都只在跑久之后显形：预算被永久
> 占住，于是所有关联慢慢开始丢数据报且查不出原因；等在收队列上的读者永远醒不过来，
> 连同它的上游 socket 一起泄漏。

### 9.4 关联的寿命 —— 两条回收路径，缺一不可

**一、流结束即关联结束。** 承载关联的那条流一旦终止（收到 `STREAM_FIN`、
收到 `STREAM_RST`、或本端主动关闭），实现 MUST 立刻结束该关联：唤醒所有等在
收队列上的读者、关掉为它开的上游 socket、把流从并发计数里摘掉。

**二、空闲即回收。** 关联在任一方向都没有流量达到空闲上限时，实现 MUST 把它
整条回收（两个方向一起）。任一方向的流量 MUST 把计时顶回去。
空闲上限 MUST NOT 短于 2 分钟，SHOULD 取 5 分钟或更长。

> 两条各挡一类：第一条管正常关闭，第二条管对端一声不吭地消失（客户端崩了、
> 路径断了、或者干脆是个恶意实现，`FIN` 永远不会来）。少任何一条都留一个完整的洞。
> SOCKS5 的实现踩过同一个坑——某家服务的事故复盘里写得很直白：他们同时依赖
> "TCP 连接关闭"和"空闲超时"，而**两条都没配好**，于是 `node_sockstat_UDP_inuse`
> 爬到两万八，DNS、NTP、隧道接连失效，而 CPU/内存/磁盘/HTTP 健康检查全是绿的。
>
> 第一条并非新发明：RFC 1928 就规定 UDP 关联在承载 `ASSOCIATE` 请求的那条 TCP
> 连接终止时终止。本协议里关联**本来就是**一条流，那就该是"流结束 = 关联结束"。
> ⚠️ 它极易被漏掉，因为 TCP 流那边不需要任何额外代码——`io.Copy` 读到 EOF 自然
> 就关了；而 UDP 这条路上根本没有 EOF 这个概念，`FIN` 只会把一个标志位置上，
> 收队列的读者不看它。本实现漏了这一步，代价是**每一次正常关闭都漏一条流**：
> 一条长命会话每做一次 DNS 查询漏一条，攒够 §4.1 的并发流上限之后
> **连 TCP 流都开不出来**（上限是共用的），而用户看到的只是"用着用着就连不上了"。
>
> 空闲上限的取值照 RFC 4787 REQ-5：NAT 的 UDP 映射定时器 MUST NOT 短于 2 分钟，
> RECOMMENDED 默认 5 分钟以上。定短了会打断长命 UDP 会话（游戏、静默期长的 QUIC），
> 而那种失败同样是静默的，只表现为"过一会儿就断"。
>
> ⚠️ 超时的处置是回收**整条关联**，不是让某一个方向的搬运停下来。
> 本实现原先给上游 socket 设了 2 分钟读超时、超时就让上行协程 `return`，
> 而下行那半边还堵在收队列上，于是上游 socket 不会被关、关联也不会被摘掉。
> 结果不是"关联被回收"而是"关联**半死**"——客户端还能往外发，回包却再也回不来，
> 两端都不报错。这比泄漏更难查。

## 10. UDP

```
DATAGRAM payload {
    addr : SOCKS5 地址格式（ATYP + ADDR + PORT）
    data : bytes
}
```

`stream_id` 即关联标识，由 `STREAM_OPEN(kind=1)` 建立。

身份信息挂在**会话**上，而非每个数据报上。因此不存在 SOCKS5 UDP 中继那个已知问题——
那里的中继是共享 socket、数据报不携带认证，客户端不得不在 ASSOCIATE 请求中申报
真实来源地址来让服务端做 `addr → user` 归属（参见仓库根 `CLAUDE.md` 关于 Windows 侧
SOCKS UDP 的说明）。那条链路上任何一环申报错了都不会报错，只是 `IN-USER` 规则对 UDP
静默失配。TIDE 中该问题在架构上不存在：归属是结构决定的，不需要申报。

| §9.4 关联寿命：流结束即结束 + 空闲即回收 | 前者缺失时**每一次正常关闭都漏一条流**（6/6 实测），攒满上限后连 TCP 都开不出来；后者缺失时对端不发 FIN 就永远收不回 |

### 11.3 实测数据

树莓派 5（arm64，客户端）↔ x86 Ubuntu（服务端），千兆 LAN，
`netem` 只作用于目的端口 8443（TCP 与 UDP 同时受损），4 条并发流，25–60 秒。

**⚠️ 读这些数字之前必须知道的两件事：**

1. **尾部分位在有损链路上的run-to-run 方差很大。** 同一份代码、同样的 5% 丢包，
   40 秒的重复实验里 p99 在 172ms–654ms 之间摆。**单次测量的 p99 不足以支撑结论**，
   下表里 p50/p90 是稳定可复现的，p99 及以上只能当量级参考。
2. **`tc qdisc … root` 只作用于出方向。** 早期实验只在客户端加了 netem，
   于是"5% 丢包"实际是**单向**的——服务端回程干净，服务端因此看不出 TCP 路径有问题、
   也就没有理由把回程迁到 QUIC。这让 TCP 残留份额虚高（14–17%）。
   加上服务端出方向的同等损伤（`match ip sport 8443`）之后，
   同一场景 TCP 残留降到 5%，尾部反而更好。**双向损伤才是有效的对照。**

**持续 5% 丢包下的往返时延分布（单向损伤，早期实验）：**

| 配置 | p50 | p90 | p99 | p99.9 |
|---|---|---|---|---|
| 无损伤基线（单 TCP） | 0.71ms | 0.95ms | 1.52ms | 3.92ms |
| 单 TCP 路径 | 1.11ms | 197ms | 619ms | 760ms |
| 双 TCP 路径（冗余） | 1.05ms | 120ms | 323ms | 455ms |
| TCP + QUIC，按丢包率迁移 | 1.26ms | 187ms | 537ms | 641ms |
| TCP + QUIC，按评分迁移（单 QUIC 流） | 1.04ms | 9.0ms | 194ms | 237ms |

**与裸 TCP 的对照（同一份测量代码、4 条并发流）：**

| 场景 | 配置 | p50 | p90 | p99 | p99.9 |
|---|---|---|---|---|---|
| 无损伤 | 裸 TCP | 401µs | 500µs | 598µs | 864µs |
| 无损伤 | TIDE | 757µs | 996µs | 1.53ms | 4.54ms |
| 5% 单向 | 裸 TCP | 414µs | 8.8ms | 279ms | 1.38s |
| 5% 单向 | TIDE，单 QUIC 流 | 1.08ms | 8.6ms | 360ms | 571ms |
| 5% 单向 | **TIDE，每流一条 QUIC 流** | 977µs | **1.67ms** | 206ms | 358ms |
| 5% 双向 | 裸 TCP | 501µs | 106ms | 330ms | 647ms |
| 5% 双向 | **TIDE，每流一条 QUIC 流** | 1.09ms | **37ms** | 312ms | 454ms |

三条结论：

- **无损伤时 TIDE 的固有开销约 0.36ms/往返**（757µs vs 401µs）。这是复用 + 会话层
  可靠性 + 调度的全部代价，亚毫秒量级。
- **"几百毫秒"不是 TIDE 造出来的。** 同一条链路上裸 TCP 的 p99 也有 279–330ms、
  p99.9 到 1.38 秒。那是 Linux TCP **200ms 最小 RTO** 的地板：LAN 上 RTT 只有 0.4ms，
  一次丢包却要等 200ms 才重传。
- **每流一条 QUIC 流是关键的一步。** 单 QUIC 流版本的 p99 反而比裸 TCP 差
  （360ms vs 279ms），因为对照组是 4 条独立 TCP 连接、一条丢包只卡自己，
  而单流版把 4 条流全塞进一条。分流后 p90 从 8.6ms 降到 **1.67ms**。

**完全断网的恢复开销**（`max RTT − 断网时长`，即链路恢复到首个数据块完成往返）：

| 断网时长 | 恢复开销 | 重连次数 | 数据完整性 |
|---|---|---|---|
| 5 秒 | 11ms | 1 | 零丢失 |
| 20 秒 | 225ms | 1 | 零丢失 |
| 60 秒 | 274ms | 1 | 零丢失 |
| 25 秒（宽限期设为 10 秒） | — | — | 干净失败：`session grace period expired` |

## 12. 未定项（draft-02 前待决）

draft-00 的五个未决项均已在本版定稿：票据位图多节点同步见 §12.1、
填充分布数据来源见 §12.2、kTLS 回退见 §12.3、票据耗尽降级见 §12.4、
迁移期乱序边界见 §4.2。以下是**本版新增**的待决项。

### 12.1 已定稿：票据位图的多节点同步

单机用内存位图。集群 MUST 提供一个满足以下契约的实现：

- **只读查询** `PeekAny(ticket_id) → (seed, user, ok)`：取出票据密钥，**MUST NOT 置位**；
- **原子测试并置位** `ConsumeAny(ticket_id) → (seed, user, ok)`：同一 id 并发只能有一个 `ok=true`；
- 票据编号必须在集群内**全局单调**分配，且这个单调性 MUST 跨进程重启保持
  （见 §3.3 的鸡生蛋说明）。

⚠️ **两个操作缺一不可，只提供合并的"查并消费"是不够的。** §3.3 要求的顺序是
"只读取密钥 → 解密（证明持有）→ 原子置位"；只有合并接口的话，第一步就不得不提前消费，
于是任何人都能用一个百来字节的伪造帧烧掉任意一张票据（`ticket_id` 是明文且可预测）。
参考实现实测过：32 张票据被 32 个垃圾帧烧得一张不剩。

> **重启**：位图是服务端硬状态，丢了就等于所有未消费票据作废——客户端的 0-RTT 会
> 干净地失败并退回 1-RTT（§12.4），这是安全的降级，不是故障。
> 但编号的单调性**必须**跨重启保持：若重启后编号从头再来，新批次会占用旧批次用过的
> 编号区间，按 `ticket_id` 反查批次这件事就不再唯一。单机内存实现因为状态整体归零
> 而天然自洽；任何**持久化**实现都要把发号器一起持久化。

参考实现路线：Redis `SETBIT`（查用 `GETBIT`，消费用 Lua 保证测试并置位的原子性），
或按 `user_id` 一致性哈希把同一用户钉在同一节点（后者不需要共享状态，
但会牺牲负载均衡的自由度）。

### 12.2 已定稿：填充分布的数据来源

分布**不做在线拟合**，而是一张编译期常量表，随协议版本走（当前 `profile_version = 1`）。
两条理由：① 在线拟合要采样本机真实流量，是隐私问题，也让不同用户的填充行为可区分；
一张所有实现共用的静态表反而让所有 TIDE 客户端在这一维上**互相不可区分**。
② 分布只需要"像"，不需要"准"——只要落在 HTTPS 的支撑集内且大致同形，
多几个百分点的 KL 散度不改变分类器的结论。

更新该表 MUST 同时递增 `profile_version`，否则新旧客户端在同一时期呈现两种分布，
反而制造了一个可分的特征。

### 12.3 已定稿：kTLS —— **在本协议里做不到，且不该再列为待办**

原计划是"bare 模式解锁 kTLS，数据在两个 kTLS socket 之间 `splice()`，用户态完全不
接触负载"。查证之后这条**站不住**，两个原因各自独立、各自致命：

1. **splice 与多路复用互斥。** `splice()` 要成立，前提是这条 TLS 连接里流动的字节
   **恰好就是**某一条被代理连接的字节。TIDE 是多路复用协议：一条路径上交替着多条流
   的帧，每帧还带 type/flags/length/stream_id 头。用户态必须解帧才知道哪几个字节属于
   哪条流——既然必须解帧，就必然要把数据读进用户态，`splice()` 无从谈起。
   这一条与 kTLS 能不能用无关，是协议形态决定的。只有"一条连接一条流"的协议
   （Trojan、不开 mux 的 VLESS）才拿得到这个收益。
2. **Go 标准库不提供 TLS 流量密钥。** kTLS 要把记录层密钥交给内核，而 `crypto/tls`
   只有未导出的 `setReadTrafficSecret`/`setWriteTrafficSecret`，没有任何导出 API，
   全库零 kTLS 支持。要拿到密钥只能 `go:linkname` 进内部符号——跨 Go 版本随时会碎，
   而它保护的是加密密钥，碎的方式不会是编译错误。

**bare 模式仍然是对的，只是收益要重新表述**：省掉内层 AEAD 的 CPU、以及消掉内层
的包长指纹。这两项都实打实，且已经拿到了。至于"零拷贝转发"，那需要一个非复用的
协议形态，与 TIDE 的会话层设计根本冲突——不是排期问题。

### 12.4 已定稿：票据耗尽的降级

**退回 1-RTT，MUST NOT 阻塞等待补充。**
弱网下补充帧本身就可能丢；耗尽时若选择阻塞，一次补充帧丢失就会让所有新连接卡死到超时，
而 1-RTT 只是多花一个 RTT。用可预测的一点延迟换掉一个不可预测的挂死，这个交换永远划算。

客户端 SHOULD 在剩余量跌破 25% 时发 `TICKET_REQUEST`。

⚠️ **服务端 MUST NOT 逐帧响应 `TICKET_REQUEST`**，MUST 合并并限速；
客户端与服务端 MUST 分别给"钱包批次数"与"单用户活跃批次数"设上界。

> 这是全协议里放大倍数最高的一处，值得写成 MUST 而不是留给实现。
>
> `TICKET_REQUEST` 的线上大小是 **4 字节**（type + flags + `length`=0 + `stream_id`=0）。
> 而它要求服务端做的事是：签发一批票据（默认 1024 张的消费位图 + 索引项，约 330 字节，
> **留存 `TicketLifetime` = 24 小时**）、读一次密码学随机数、再回一个 42 字节的
> `TICKET_REPLENISH`。逐帧响应的账是：
>
> | 维度 | 攻击方付出 | 受害方付出 | 倍数 |
> |---|---|---|---|
> | 内存 | 4 B | ~330 B × 24 小时 | **80×** |
> | 回程带宽 | 4 B | 42 B | **10×** |
> | 并发 | 4 B | 一个协程 / 线程 | 无上界 |
> | CPU | 4 B | 一次 CSPRNG 读取 + 一次库写入 | — |
>
> 全程不触发任何错误路径，也不越过任何既有配额——这正是 RFC 9000 §21.9 描述的形态：
> *"处理开销相对于带宽消耗或状态变化不成比例，就可能让恶意对端耗尽处理能力"*，
> 其给出的处置是 *"实现 SHOULD 跟踪处理开销与实际进展的比值"*。
>
> 合并是安全的，因为"请给我补票"**是幂等的**：收到 1 次和收到 1 万次，要做的事一模一样。
> 因此正确形状是一个容量为 1 的信号 + 一条会话一个消费者 + 最小补发间隔，
> 而不是每帧一个执行单元。
>
> 上界不能改成"按需签发"（比如服务端查一下这个用户还剩多少再决定）：
> `TICKET_REPLENISH` 本身可能丢，那时服务端以为客户端有、客户端其实没有，
> 按需判断会让它**永远**拒绝补发，客户端就永久退回 1-RTT。限速不会有这个问题，
> 丢了的那批下一个间隔就会重来。

### 12.5 已定稿：QUIC 路径的流映射 —— 每条 TIDE 流一条 QUIC 流

早先一条 QUIC 路径只映射**一条** QUIC 流，路径内部因此仍有队头阻塞。
实测把代价量了出来（4 条并发流、5% 丢包）：TIDE 的 p99.9 已经比裸 TCP 好 2.4 倍，
**p99 却更差**（360ms vs 279ms）。差在对照组是 4 条独立 TCP 连接、一条丢包只卡自己，
而 TIDE 把 4 条流全塞进一条 QUIC 流、一个丢包卡住全部四条。
复用省下的连接数是拿队头阻塞换的，并发流越多越亏。

现在每条 TIDE 流有自己的 QUIC 流，控制帧（握手、探测、票据）留在第一条流上。
`DATAGRAM` 也留在控制流——它虽然带 assoc 的流号，但 UDP 语义上不该被重传，
真正正确的做法是走 QUIC 数据报（见 §12.8）。

QUIC 路径因此**无条件使用 `bare` 内层**，且不受 `AllowBare` 开关约束：
多条 QUIC 流之间没有全局顺序，`sealed` 的按路径 nonce 序号必然错位。
安全性上这站得住——QUIC-TLS **恒定**提供 AEAD（不像裸 TCP 那样可能没有），
且信道绑定已证明外层未被中间人替换，正是 §6.2 允许 `bare` 的两个前提。

⚠️ 随之而来的一条约束：**`bare` 是每路径的属性，不是每会话的。**
一个会话可以同时挂着 sealed 的 TCP 路径和 bare 的 QUIC 路径。
实现中若用会话级的 `bare` 去建路径的记录层，两端会立刻对不上，
而报错长得像"解密失败"，会把排查方向指到密钥调度上去。

### 12.6 部分定稿：QUIC 路径的主动探测防御

**已定的部分：QUIC 路径 MUST 只能加入已有会话，MUST NOT 新建会话。**

QUIC 面不做 §7 的掩护转发——掩护对象只能是另一个 QUIC/HTTP-3 服务，字节流也不能
直接搬过去（QUIC 有自己的流语义）。既然它没有伪装，就不该是一个可以独立进入的入口。
强制"必须先有会话"之后，探测方无论怎么打这个 UDP 端口都拿不到东西：它没有会话 ID，
而会话 ID 只能通过 TCP 那条**有掩护**的路径认证后取得。
这把"QUIC 只是加速通道"从一句部署建议变成了协议强制的性质。

认证失败时服务端 MUST NOT 立刻关闭 QUIC 连接——立刻关是一个可测量的、
与"真实服务在等后续请求"截然不同的行为。应当读到对端自己放弃为止（§7.2 同款处理）。

**仍然待决的部分：残留差距，以及唯一可行的解法。**

上述措施让 QUIC 端口"什么也给不出"，但**没有**让它看起来像别的东西：
探测方仍能确认「这个 UDP 端口上有一个会完成握手、但对 h3 请求沉默的 QUIC 服务端」。
而一台在 TCP/443 上服务 HTTPS 的主机，在 UDP/443 上跑一个不响应 h3 的 QUIC 端点，
本身就是异常的。

**唯一可行的解法是把 TIDE 的 QUIC 面整个搬到 HTTP/3 之上**，而不是"在旁边加一个 h3
服务器"。原因是判别问题无解：h3 的请求流以 HEADERS 帧（类型 0x01）开头，
TIDE 的 HELLO 也是 0x01；一旦为了判别而消费掉第一条双向流，就再也无法把它交还给
h3 服务器，探测方发的那个请求会挂死——比沉默更可疑。

具体方案（quic-go v0.61 的 API 已核实存在）：

| 需要的能力 | quic-go 提供 |
|---|---|
| 服务端接管已认证请求的底层流 | `http3.HTTPStreamer.HTTPStream() *Stream` |
| 服务端自持 `*quic.Conn`（信道绑定要用） | `http3.Server.ServeQUICConn(conn)` |
| 客户端自持 `*quic.Conn` | `http3.Transport.Dial` 钩子 |

- 每条 TIDE 流 = 一个 h3 请求（与 §12.5 的每流一条 QUIC 流天然 1:1）。
- 服务端 handler：认证通过 → 劫持流跑 TIDE；否则 → 反向代理到掩护源站。
  于是**服务端对任何非 TIDE 客户端都是一个货真价实的 h3 服务器**。
- 「行为古怪的 h3 服务器」这个担心不成立：h3 行为来自 quic-go 自己的实现，
  与 Caddy 用的是同一套，不是手搓的。

⚠️ 这个改动会连带影响 §12.8：h3 之上的数据报必须走 RFC 9297 的 HTTP Datagram
（带 Quarter Stream ID 前缀），不能直接用裸 QUIC 数据报。

**已实施并通过测试，但仍默认关闭。**

- ✅ **掩护**：`Server.ServeH3` 让服务端对任何非 TIDE 的 HTTP/3 客户端反向代理到
  掩护源站——实测探测方拿到 `200` + 源站真实的 `Server:` 头与正文，
  不是沉默、也不是模拟。§12.6 的安全目标达成。

  ⚠️ **但入口路径 MUST 由服务端静态公钥导出，MUST NOT 是协议常量。**

  > 上面那句"对任何非 TIDE 客户端都是一个货真价实的 h3 服务器"有一个例外，
  > 而这个例外一度是全网通用的：TIDE 的入口路径曾经写死成一个常量
  > （本实现里是 `/api/v1/stream`）。落在加密的 h3 请求头里，被动观察者确实看不到，
  > 但主动探测方不需要看——**猜一次就够，而且猜中一次就等于拿到全网扫描的判据**，
  > 因为它在每一个部署上逐字节相同。这与占位掩护页、以及握手帧的固定长度是同一类
  > 错误：一个到处一样的常量就是指纹。
  >
  > 打中之后的行为使它更糟：服务端在**认证之前**就把 `200` 发出去（客户端要等
  > 响应头才敢写请求体），认证失败后只能把连接晾着。探测方于是拿到
  > "`200 OK` + 空正文 + 永不关闭"——真实站点上不存在的路径会 404，
  > 真的流式接口会发点什么，两样都不是。实测负对照打出来正是 `200` + 0 字节。
  > NDSS'20 *Detecting Probe-resistant Proxies* 量过这个方向：网上超过 94% 的服务器
  > 会对某个常见协议回数据，"不回数据"本身就是可用于识别的异常。
  >
  > 处置照 Caddy forwardproxy 的 `probe_resistance`：没有凭据的请求一律当成普通
  > 网站伺候，而代理入口藏在一个只有持密者知道的**秘密地址**后面（Caddy 用
  > secret-link 域名）。本协议的"密"现成就有——服务端静态公钥，客户端配置里本来
  > 就带着它，不需要任何新配置项，也不增加任何往返。
  >
  > 于是：猜不中就没有任何区别性行为可测（一律走掩护反代）；要猜中就得先有公钥，
  > 而那已经是共享秘密。认证失败那条路**仍然**不做掩护反代（`200` 已经发出去了，
  > 源站的状态码与响应头没地方放），这一点必须写清楚而不是含糊过去——
  > 它可以接受，仅仅因为走到那里的前提是已经持有公钥。
- ✅ **数据面**：TIDE 的流在 h3 之上收发正常，60 KB 净荷字节级完整往返。

**数据面已修复（见下），但仍默认关闭——原因只剩 RFC 9297。**

曾经的"h3 路径建起来就死"由两个各自独立的 bug 叠成，都是**同一个问题被回答了两遍**：

1. `finishHandshake` 里"这是不是 QUIC"被问了两次：一处用 `isQUICConn`（含 h3，
   于是**告诉客户端用 bare**），另一处用窄的 `*quicConn` 断言（h3 不匹配，
   于是**服务端建了 sealed 记录层**）。两个答案隔着 70 行，结果是服务端发密文、
   客户端当明文读。报错是 `frame exceeds max size`，指向解帧，
   与 bare 协商差着十万八千里——靠打印原始字节（高熵 = 密文）才认出来。
2. 服务端 h3 侧压根没装分流器（只在 `nativeQUIC` 时装），于是 `serveData` 把每条
   数据流原地丢掉。现象是控制流通着、路径活着，数据一个字节都不过。

修完之后 `-race -count=25` 连续通过，原先约 1/4 的不稳定消失。

实网测量（树莓派 5 ↔ x86，**双向** 5% 丢包，40 秒，4 条流）：

| 模式 | p50 | p90 | p99 | p99.9 | 路径建立次数 | h3/QUIC 路径承载 |
|---|---|---|---|---|---|---|
| 原生 QUIC | 1.05ms | 23ms | 306ms | 462ms | 2 | — |
| h3 **修复前** | 75ms | 606ms | 1.59s | 2.18s | **9** | 0（全退回 TCP） |
| h3 **修复后** | **1.03ms** | **23.9ms** | **389ms** | **594ms** | **2** | **75.1 MiB / 共 80** |

修复后 h3 与原生 QUIC 基本同档：p50 完全一致，p90 相差 1ms，p99/p99.9 略高但仍在
本文档开头说明的 run-to-run 方差范围内（同一份代码同样丢包，p99 在 125–654ms 之间摆）。
"路径建立 2 次"是关键：churn 消失了。

**最后挡着转正的那件事——接 RFC 9297 的 HTTP Datagram——已经做完。**
在此之前 h3 模式下 `DATAGRAM` 走可靠有序的控制流，与 §9.1「UDP MUST NOT 重传」相悖：
被代理的 QUIC 跑在可靠通道上会出现两层拥塞控制打架。那是功能缺口，不是洁癖。

**已接上并稳定（`-race -count=25` 连续通过）。**

实现要点与一个必须知道的约束：客户端**不能**混用 `Transport.RoundTrip` 与
`NewClientConn`——后者会自己开一条 h3 控制流并发 SETTINGS，同一条 QUIC 连接上
两条控制流就是 h3 协议错误。所以客户端整体换到了
`NewClientConn` + `OpenRequestStream`：这样才拿得到 `*RequestStream`，
而 RFC 9297 的数据报是**绑在具体请求流上**的，`resp.Body` 够不着。
副作用是好的——`RequestStream` 本身双向，去掉了原先 `io.Pipe` + `resp.Body` 的拼装，
h3 路径的回程字节也随之正常了（此前 rx 恒为 0）。

数据报绑在**控制流**上：两端必须用同一条，而控制流是唯一双方都确定存在、
且生命周期与路径一致的那条。

**残留问题已定位并修好，与 SETTINGS 无关。**

原先怀疑是 datagram 能力协商完成前发出的数据报被静默丢弃（quic-go 的 `SendDatagram`
里确实留着 `TODO: reject if datagrams are not negotiated (yet)`）。**打点之后这条被证伪**：
两端都在握手结束前就拿到了对方的 SETTINGS，`EnableDatagrams` 均为 `true`，
`SendDatagram` 每次都返回 `nil`，服务端也确实收到了。

真正的原因是 §9.2 那条——**第一个数据报比它自己的 `STREAM_OPEN` 先到**，
服务端找不到关联就把它丢了。之所以看起来是"一半概率"，是因为两条路径的时序在
本机回环上恰好势均力敌；`-race` 一开，抢跑变成常态，失败率就上去了。
（同时还有一个把它伪装成"超时"的测试缺陷：`SetReadDeadline` 设在重试循环**外面**，
而它是绝对时刻不是等待时长，于是"重试 10 次"实为"试 1 次然后空转 9 次"，
失败恰好耗时 10 秒。两个问题叠在一起，才让人一路怀疑到 SETTINGS 上去。）

处置见 §9.2：按 RFC 9297 §5.2 的同款做法，在一个 RTT 量级内暂存等待关联建立，
带条数与字节数双上界。修复后 `-race -count=25` 连续通过，测试也不再需要环境变量常关。

下面是当初核实 API 时的记录，保留备查：

| 需要 | quic-go 提供 | 备注 |
|---|---|---|
| 收发 HTTP Datagram | `http3.Stream.SendDatagram` / `ReceiveDatagram` | **Quarter Stream ID 前缀由它自己加**，不用手写 RFC 9297 的封装 |
| 客户端拿到 `*http3.Stream` | `http3.ClientConn.OpenRequestStream(ctx)` → `*RequestStream` | 官方注释写明用途就是"在收到响应之前就能用这条流发数据报" |
| 两端开启 | `http3.Transport.EnableDatagrams` / `http3.Server.EnableDatagrams` | 同时还要在 QUIC 层 `quic.Config.EnableDatagrams`（当前 `h3QUICConfig()` 把它关掉了，要打开） |

唯一有分量的改动是**客户端要从 `Transport.RoundTrip` 换成 `ClientConn.OpenRequestStream`**：
现在的 `openH3Stream` 靠 `io.Pipe` + `resp.Body` 拼出双向流，换成 `RequestStream` 之后
才拿得到底层的 `*http3.Stream`。风险点在于控制流同时承载握手，
改它等于动整条路径的建立流程——建议先只把**数据报**切过去、握手仍走原路，验证通过再统一。

实现过程中撞到并记下的**四个**坑，都属于"不写下来下次还会再踩"：

0. **h3 请求的生命周期必须绑到路径，不能绑到拨号 ctx。** 控制流就是那个 HTTP 请求
   本身；调用方在拨号返回后立刻 `cancel()` 掉拨号 ctx，路径就在**建起来的同一瞬间
   被拆掉**——现象是"h3 路径起来就死"。原生 QUIC 路径不受影响，因为
   `DialAddr`/`OpenStreamSync` 的 ctx 只约束等待、不决定流的存活；
   这个不对称正是它最难被想到的地方。

1. **`MaxIncomingUniStreams` 必须放开。** HTTP/3 靠单向流承载控制流与 QPACK 流
   （RFC 9114 §6.2）。原生模式那份配置把它设成 -1（禁用），客户端开不出控制流，
   握手以 `H3_INTERNAL_ERROR` 告终——而且错误是**客户端本地**产生的，
   看日志会以为是客户端的问题。
2. **劫持前必须 Flush 响应头。** quic-go 的 responseWriter 会缓冲小响应，
   不冲刷则响应头要等 handler 返回才发出——而 handler 正阻塞在 TIDE 握手上等
   客户端发 HELLO，客户端又在等响应头才敢开始写。双方互等，死锁。
3. **反代必须剥掉逐跳头。** `Connection`/`Transfer-Encoding` 之类在 HTTP/2、
   HTTP/3 里是非法的，原样搬过去会让规范的 h3 客户端直接断连——
   那恰好制造出我们想消除的"异常端点"信号。

### 12.7 已定稿：拥塞控制 —— **不指定算法，且默认不动系统默认值**

design.md 写的是"拥塞控制明确用 BBRv3"。落地时发现两件事，合起来把这条推翻了：

1. **QUIC 侧根本换不了。** quic-go v0.61 的 `internal/congestion` 里只有 cubic，
   `Config` 不暴露任何选择接口。想换只能 fork quic-go。
2. **TCP 侧能换（`setsockopt(TCP_CONGESTION)`），但换了更糟。** 实测
   （双向 5% 丢包，40 秒，同一份测量代码）：

   | 算法 | p90 | p99 | p99.9 | TCP 路径 srtt |
   |---|---|---|---|---|
   | `bbr` | 76.2ms | 620ms | 811ms | 21.71ms |
   | `cubic`（系统默认） | 22.7ms | **125ms** | **203ms** | **1.29ms** |

   BBR 把尾部差了 5 倍。关键在于 design.md 说的是 BBR**v3**，而 Linux 内核里的
   `bbr` 是 **v1**——v1 对随机丢包（非拥塞丢包）的处理正是它的已知弱点：
   持续探测带宽把队列撑起来，在浅队列上反而制造突发丢包，RTT 膨胀一个数量级。

因此实现提供 `Congestion` 配置项，但**默认为空（不动系统默认）**。
一个只在特定内核 + 特定链路上才可能有收益、而在实测链路上明确有害的优化，
不该是默认值。

规范层面仍然保留 §8 的那条约束：**MUST NOT 默认启用无上界的激进拥塞控制**
（针对 Brutal 那一类），这条与"不指定具体算法"并不矛盾。

### 12.8 已定稿：`DATAGRAM` 走 QUIC 数据报

**两条数据面都已落地。** 原生 QUIC 路径走 RFC 9221 的 QUIC 数据报
（`quicMux.sendDatagram` / `datagramLoop`），h3 路径走 RFC 9297 的 HTTP Datagram
（§12.6）。`DATAGRAM` 不再被塞进可靠有序的流里，§9.1 在实现上成立。

当初挂着不做的顾虑是"QUIC 数据报有 MTU 上限、要自己处理分片与丢弃"。落地时的处置是
**超限即回退到可靠流**，而不是丢弃：真实世界里超过 MTU 的 UDP 会被 IP 分片而不是消失，
静默丢会让带很多记录的大 DNS 应答无声失败。代价是那一小部分数据报"意外地可靠了"，
这个取舍比静默丢包好，且只影响大包。

⚠️ 一条必须一起做的配套：**观测量要把数据报字节和流字节分开记**
（`PathInfo.TX/RX` 与 `TXDgram/RXDgram`）。"UDP 有没有被偷偷塞回可靠流"唯一能用的
证据就是「总量 − 数据报量 = 流字节」这个差；只有一个总数时，"没走流"和"根本没发出去"
长得一模一样——而这两件事一个是对的、一个是彻底坏了。
曾经 h3 侧的数据报发送根本不计入任何计数器，于是那条断言是靠**漏记**才通过的。
